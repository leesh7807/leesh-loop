# 2026-10-11-local-task-store-foundation

## Objective

leesh-loop에서 현재 Notion이 담당하는 작업 데이터 저장 기능을 로컬 SQLite 기반 작업 저장소로 대체하기 위한 첫 단계를 구현한다.

현재 Notion 작업 모델에서 실제로 필요한 데이터와 동작만 수용하고, 불필요한 외부 서비스 종속 구조와 범용 문서·데이터베이스 기능을 제거한 단순한 로컬 저장소를 구축한다.

이번 작업은 저장소 자체의 완성을 목표로 하며, 기존 Notion 기반 작업 실행 경로의 전환은 포함하지 않는다.

## Intent

leesh-loop의 핵심 자산은 사용자가 정의하는 `WORKFLOW.md`이며, 작업 저장소는 해당 워크플로를 실행하는 시스템을 뒷받침하는 구성 요소다.

현재 Notion은 작업 상태, Accepted Plan, Workpad, 댓글, 작업 관계를 저장하는 역할을 수행한다. 그러나 외부 SaaS를 작업 실행의 필수 저장소로 사용하기 때문에 API 제한, 네트워크 지연, 외부 인증, 데이터 모델 제약 및 불필요한 기능적 복잡성을 감수하고 있다.

작업 저장소를 로컬로 소유하고 제어할 수 있다면 이러한 제약을 줄일 수 있다. 또한 이후 Operator Panel을 작업 관리의 기본 인터페이스로 발전시키기 위한 기반이 된다.

사용자는 작업 데이터를 직접 SQLite 도구로 편집하는 것이 아니라, 최종적으로 Operator UI를 통해 조회하고 조작한다. 다만 현재 Operator UI는 작업 상태 변경과 댓글 작성 등 Notion이 담당하는 기능을 모두 제공하지 않으므로, 저장소 구축과 기존 실행 경로의 전환을 분리한다.

이번 단계에서는 실제 작업을 로컬에 저장할 수 있는 기반을 먼저 완성한다. 이후 별도의 작업에서 Operator UI, Symphony Adapter, Worker 도구를 로컬 저장소에 연결한다.

이 시스템은 분산 작업 관리나 다중 사용자 협업을 목표로 하지 않는다. 각 Loop 인스턴스는 서로 독립적인 작업 환경이며, 컴퓨터 간 상태 동기화나 원격 조작은 고려하지 않는다.

기존 Notion의 기능을 동일하게 복제하는 것도 목표가 아니다. 현재 작업 수행에 필요한 의미와 데이터는 유지하되, Notion의 페이지·블록·관계형 프로퍼티 표현과 외부 API 대응 때문에 발생한 복잡성은 제거하는 방향이다.

KISS, YAGNI, DRY를 우선하며, 아직 필요하지 않은 범용 기능이나 추상화는 도입하지 않는다.

## Verification Requirements

### VR-1. 로컬 작업 데이터의 완전한 표현

현재 leesh-loop의 정상적인 작업 수행에 필요한 다음 데이터가 로컬 저장소에서 표현되고 유지되어야 한다.

- 작업의 안정적인 고유 ID
- 사용자에게 표시하는 Identifier
- Title
- State
- Priority
- Labels
- Blocked By 관계
- Accepted Plan 원문
- Workpad
- 사용자 댓글
- 필요한 생성·수정 시각

현재 Notion의 표현 방식과 동일할 필요는 없지만, 각 데이터가 현재 시스템에서 가지는 의미가 손실되어서는 안 된다.

### VR-2. 작업 데이터의 독립적 저장과 조회

작업 생성, 단건 조회, 목록 조회, 속성 변경, Workpad 추가, 댓글 추가 및 의존성 변경이 로컬 저장소만으로 가능해야 한다.

저장된 데이터는 프로세스가 종료되고 다시 시작된 이후에도 유지되어야 한다.

조회와 변경 과정에 Notion 또는 다른 외부 저장 서비스가 필요하지 않아야 한다.

### VR-3. Accepted Plan의 보존과 발행 일관성

발행된 Task는 발행 시점에 확정된 Accepted Plan 원문을 실행 입력으로 보존해야 한다.

Accepted Plan은 Task에 귀속된 불변 데이터로 관리되어야 하며, 일반 작업 속성 변경, Workpad 추가, 댓글 추가 또는 의존성 변경으로 수정되지 않아야 한다.

Accepted Plan의 보존과 조회는 대상 Git 저장소의 Plan 파일 존재 여부, 위치, 변경 또는 Worker 작업 공간의 생명주기에 의존하지 않아야 한다.

사용자는 Task를 발행하기 위해 대상 Git 저장소에 Plan 파일을 미리 생성하거나 커밋할 필요가 없어야 한다.

동일한 발행 요청으로 Task가 중복 생성되지 않아야 하며, 발행이 실패하면 불완전한 Task가 남지 않아야 한다.

### VR-4. Workpad와 댓글의 기록 의미

Workpad와 댓글은 추가 순서가 보존되는 누적 기록으로 관리되어야 한다.

기존 항목을 다시 작성하지 않고 새로운 항목을 추가할 수 있어야 한다.

각 댓글은 안정적인 고유 ID를 가져야 하며, 기존 Human Review 흐름에서 사용하는 댓글 기준점 이후의 입력을 구분할 수 있어야 한다.

Workpad와 사용자 댓글은 저장 방식을 공유할 수 있지만, 읽을 때 명확히 구분되어야 한다.

### VR-5. 작업 상태와 관계의 일관성

작업 상태, 우선순위, 레이블 및 작업 의존성을 저장하고 변경할 수 있어야 한다.

Blocked By 관계는 로컬 작업 ID를 기준으로 표현되어야 하며, 존재하지 않는 작업이나 자기 자신을 차단 대상으로 등록할 수 없어야 한다.

현재 Symphony에서 사용하는 작업 차단 여부를 로컬 데이터로 판단할 수 있어야 한다.

작업 데이터의 변경은 실패 시 부분적으로 반영된 불완전한 상태를 남기지 않아야 한다.

### VR-6. 단순한 동시 쓰기 처리

같은 작업에 여러 쓰기 요청이 들어와도 저장 데이터가 손상되지 않아야 한다.

서로 다른 Workpad 또는 댓글 추가 요청은 각각 독립적인 기록으로 보존되어야 한다.

작업마다 별도의 분산 잠금이나 복잡한 충돌 해결 체계를 요구하지 않는다.

### VR-7. Loop 인스턴스 독립성과 운영 단순성

각 Loop 인스턴스는 다른 인스턴스와 독립된 로컬 작업 저장소를 가져야 한다.

저장소를 사용하기 위해 별도의 데이터베이스 서버, 추가 포트, 외부 인증 또는 외부 서비스 설정이 필요하지 않아야 한다.

저장소는 Loop 인스턴스가 소유하는 지속 데이터로 관리되어야 하며, 일반적인 런타임 재시작이나 업데이트로 손실되지 않아야 한다.

### VR-8. 기존 실행 경로의 보존

이번 단계의 저장소 구축으로 현재 Notion 기반 Operator, Publisher, Symphony, Worker 실행 경로의 동작이 변경되지 않아야 한다.

기존 `WORKFLOW.md`의 작업 수행 정책도 변경되지 않아야 한다.

새 저장소의 존재가 기존 작업 실행의 필수 조건이 되어서는 안 된다.

## Definitions

- **Loop 인스턴스**: 하나의 대상 Git 저장소를 운영하도록 독립적으로 생성된 leesh-loop 실행 환경.
- **Local Task Store**: 하나의 Loop 인스턴스가 소유하는 SQLite 기반 로컬 작업 저장소.
- **Task**: 작업 속성, Accepted Plan, Workpad, 댓글 및 의존성을 연결하는 논리적 작업 객체.
- **Task ID**: 로컬 저장소에서 Task를 식별하는 안정적인 고유 ID.
- **Identifier**: 사용자에게 표시하는 기존 작업 식별자.
- **Accepted Plan**: Task의 확정된 실행 입력. 발행 시점의 완전한 원문으로 Local Task Store가 소유하며, 발행 이후 변경되지 않는다.
- **Git Plan 문서**: Worker가 `WORKFLOW.md`에 따라 대상 Git 저장소에서 관리하는 개발 산출물. Accepted Plan과 별도의 생명주기를 가진다.
- **Workpad**: Worker가 작업 수행 과정에서 누적하는 실행 기록.
- **Comment**: 사용자가 작업에 추가하는 입력 기록. Human Review의 입력 범위를 판별할 수 있는 고유 ID와 순서를 가진다.
- **Blocked By**: 다른 Task의 완료 여부에 따라 현재 Task의 실행 가능성을 제한하는 관계.
- **Publication**: Accepted Plan을 기준으로 Task와 관련 데이터를 완전한 상태로 생성하는 동작.
- **Operator Panel**: 사용자가 작업을 조회하고 조작하는 leesh-loop의 웹 인터페이스. 이번 단계에서는 변경하지 않는다.

## Decisions

### 1. 저장소의 소유권과 생명주기

Local Task Store는 별도의 독립 제품이나 서비스가 아니라 leesh-loop 내부 모듈로 구현한다.

각 Loop 인스턴스는 자체 SQLite 데이터베이스 파일을 소유한다.

데이터베이스는 기존 `state_directory` 아래에 저장한다. 새로운 필수 설정이나 포트를 도입하지 않는다.

저장소 초기화는 현재 Loop의 정상적인 준비 절차에 통합할 수 있어야 한다. 사용자가 별도의 데이터베이스 관리 명령을 실행하도록 요구하지 않는다.

실행 중인 저장소는 해당 Loop 인스턴스의 작업 데이터만 관리한다.

### 2. 데이터 모델의 단순화

현재 Notion DB의 필요한 프로퍼티와 데이터 의미를 기준으로 로컬 모델을 구성한다.

Task와 Accepted Plan은 일대일 관계이므로, 별도의 Notion Plan 데이터소스에 대응하는 구조를 재현하지 않는다.

Accepted Plan은 Local Task Store가 소유하는 Task의 불변 원문으로 SQLite에 저장한다. 사용자가 Plan을 발행하기 위해 대상 Git 저장소에 미리 파일을 생성하거나 커밋할 필요는 없다.

Worker가 `WORKFLOW.md`에 따라 생성하거나 관리하는 Git Plan 문서는 별도의 개발 산출물이다. Local Task Store는 해당 문서의 생성, 이동, 수정 또는 동기화를 책임지지 않는다.

Workpad와 댓글은 append-only 기록으로 관리한다.

두 기록은 구현상 하나의 저장 구조를 공유할 수 있으며, 이 경우 기록 종류와 작성 주체를 구분할 수 있어야 한다.

Blocked By는 Task ID 간 관계로 저장한다.

프로젝트 식별을 위해 모든 Task에 별도의 Project ID를 필수로 부여하지 않는다. 하나의 Loop 인스턴스가 하나의 대상 프로젝트를 운영한다는 기존 계약을 사용한다.

### 3. 발행 의미의 유지

Publisher의 핵심 책임인 Plan 유효성 검증, Task Identifier 결정, 중복 발행 방지 및 작업 생성의 완전성을 유지한다.

기존 Publisher의 Identifier 산출 알고리즘이나 Notion 전용 발행 절차를 그대로 재현할 필요는 없다. 다만 동일한 발행 요청으로 중복 Task를 생성하지 않아야 한다.

Accepted Plan은 발행 시점의 완전한 입력 원문으로 Task와 함께 원자적으로 저장한다. 별도의 Plan 파일을 생성하거나 Git 저장소에 커밋하는 것을 발행의 선행 조건으로 요구하지 않는다.

기존의 `Publisher Pending` 상태는 여러 Notion API 요청을 거치는 발행 과정의 부분 실패를 복구하기 위한 장치이므로, 로컬의 원자적 발행으로 대체한다.

Notion 데이터소스 스키마 초기화, Plan 페이지 생성, Relation 연결, 페이지 잠금 및 발행 후 API 재조회는 로컬 저장소에서 재현하지 않는다.

### 4. 작업 변경과 동시성

Local Task Store는 SQLite의 트랜잭션과 쓰기 직렬화 기능을 기본 동시성 수단으로 사용한다.

별도의 Task별 명령 큐, 분산 잠금, 버전 벡터, 병합 정책 또는 이벤트 소싱 시스템은 도입하지 않는다.

Workpad와 댓글의 append-only 기록을 모든 Task 속성에 대한 이벤트 소싱으로 확장하지 않는다.

State와 기타 현재값 속성은 일반적인 변경 방식으로 관리한다.

상태 변경의 의미적 유효성은 저장소의 쓰기 직렬화와 별개의 책임으로 취급한다. 향후 Adapter 및 사용자 조작 경로에서도 현재 작업 생명주기 계약을 유지할 수 있도록 한다.

Local Task Store는 작업 속성과 관계의 일관성을 보장한다. 작업 생명주기와 스케줄링 정책은 기존 실행 계층의 책임으로 유지한다.

### 5. 접근 계층의 역할

Local Task Store는 Operator와 Symphony가 사용할 수 있는 명확한 작업 저장 인터페이스를 제공한다.

이번 단계에서는 해당 인터페이스의 실제 저장·조회·수정 동작까지만 구현한다.

Symphony Adapter와 Worker 도구의 교체는 후속 작업으로 분리한다.

사용자의 공식적인 데이터 조작 경로는 최종적으로 Operator Panel이 된다.

SQLite 파일의 직접 편집이나 별도의 데이터베이스 관리 UI를 정상 사용 흐름으로 설계하지 않는다.

### 6. 기존 설치 환경과 데이터

이번 작업은 기존 Notion Task 데이터를 자동으로 이전하지 않는다.

Notion에서 로컬 저장소로 가져오는 기능이나 반대 방향으로 내보내는 기능도 구현하지 않는다.

기존 설치 환경은 이번 변경 이후에도 현재 Notion 기반 실행을 계속할 수 있어야 한다.

향후 로컬 Tracker로 전환할 때 필요한 설정·업데이트·워크플로 호환성 변경은 별도 계획에서 다룬다.

### 7. 보호 범위와 명명

다음은 이번 작업에서 변경하지 않는다.

- `WORKFLOW.md`의 개발·리뷰·병합 정책
- Symphony의 스케줄링과 Worker 실행 정책
- 현재 Notion Tracker Adapter의 실행 동작
- Worker에게 제공되는 기존 `notion_task_*` 도구
- 기존 Operator Panel의 사용자 흐름
- GitHub PR 및 병합 관련 동작
- chatgpt-shot과 외부 리뷰 실행 계약
- 기존 Loop 인스턴스 관리 명령의 의미

보호 범위를 넘어서는 변경은 별도 계획으로 다룬다.

새 파일·모듈·타입·주요 함수의 이름은 현재 맡는 구체적 책임을 드러내야 한다.

아직 존재하지 않는 범용 Tracker 프레임워크, 여러 저장소 구현, 원격 동기화 계층 등을 전제로 이름을 설계하지 않는다.

### 8. 구현 범위에서 제외할 기능

이번 단계에서는 다음을 구현하지 않는다.

- Notion Export/Import
- 기존 Notion 데이터 마이그레이션
- 다중 컴퓨터 간 상태 동기화
- 원격 작업 조회·조작
- 다중 사용자 협업 및 권한 관리
- 별도 데이터베이스 서버
- 별도 API 포트
- 범용 Markdown 문서 관리
- Rich Text 편집기
- 댓글 수정·삭제
- Workpad 항목 수정·삭제
- Symphony Local Tracker 전환
- Operator Panel 기능 확장
- Git Plan 문서의 생성·관리·동기화 기능
- 실행 로그·Worker 세션 관리 UI

## Planned Units

### 1. 로컬 작업 저장과 조회

Task의 식별자, 기본 속성, Accepted Plan 및 작업 관계를 SQLite에 영속적으로 저장하고 조회하는 기능을 완성한다.

작업 발행은 완전한 Task를 원자적으로 생성하며, 동일한 발행 요청에 따른 중복 Task 생성을 방지한다.

Accepted Plan은 대상 Git 저장소의 파일과 독립적으로 보존한다.

**독립적인 결과:** Notion이나 별도의 Plan 파일 없이 로컬 작업을 발행하고, 속성을 변경하고, 종료 후 다시 조회할 수 있다.

### 2. Workpad와 사용자 입력 기록

Task에 연결된 append-only Workpad 및 댓글 기능을 완성한다.

두 기록의 순서를 보존하고, Human Review에서 사용할 댓글 기준점 이후 조회를 지원한다.

**독립적인 결과:** 하나의 Task에 여러 기록을 누적하고, 재시작 이후에도 순서와 식별자를 유지하면서 필요한 기록을 구분해 읽을 수 있다.

### 3. Loop 인스턴스 통합

Local Task Store를 Loop 인스턴스의 지속 데이터로 통합한다.

인스턴스별 저장소 독립성, 초기화, 재시작 및 업데이트 시 데이터 보존을 확보한다.

기존 Notion 기반 실행 경로는 그대로 유지한다.

**독립적인 결과:** 각 Loop 인스턴스가 별도 서비스나 설정 없이 로컬 저장소를 소유하고 사용할 수 있다.

## Verification

### VR-1. 로컬 작업 데이터의 완전한 표현

현재 Notion Adapter 및 Publisher가 사용하는 Task 데이터 계약을 기준으로 대표 Task를 구성한다.

모든 필수 속성, Accepted Plan, Workpad, 댓글 및 Blocked By 관계를 저장한 뒤 읽어 원래 의미와 값이 보존되는지 확인한다.

Notion 고유 표현 없이 필요한 데이터가 모두 복원되면 통과한다.

### VR-2. 작업 데이터의 독립적 저장과 조회

실제 SQLite 파일을 이용해 다음 작업을 수행한다.

1. Task 생성
2. 단건 및 목록 조회
3. 속성 수정
4. Workpad 추가
5. 댓글 추가
6. 의존성 변경
7. 저장소 연결 종료와 재개
8. 전체 데이터 재조회

외부 서비스에 접근하지 않고 모든 데이터가 기대한 상태로 복원되면 통과한다.

### VR-3. Accepted Plan의 보존과 발행 일관성

Plan 원문을 이용해 Task를 발행하고, 저장된 Accepted Plan이 발행 입력과 정확히 일치하는지 확인한다.

대상 Git 저장소에 Plan 파일이 없고 Worker 작업 공간도 존재하지 않는 상태에서 발행과 조회가 가능한지 확인한다.

발행 이후 작업 속성 변경, Workpad 추가, 댓글 추가 및 의존성 변경을 수행하고 Accepted Plan 원문이 변하지 않았는지 확인한다.

동일한 발행 요청을 반복하거나 동시에 수행하여 중복 Task가 생성되지 않는지 확인한다.

발행 과정에서 의도적으로 오류를 발생시켜 불완전한 Task가 남지 않는지 확인한다.

### VR-4. Workpad와 댓글의 기록 의미

한 Task에 Workpad와 댓글을 교차하여 추가한다.

전체 조회 및 종류별 조회에서 추가 순서가 보존되는지 확인한다.

댓글 기준점을 선택하고 그 이후 추가된 댓글만 정확하게 조회되는지 확인한다.

저장소를 재연결한 뒤에도 ID와 순서가 동일하게 유지되면 통과한다.

### VR-5. 작업 상태와 관계의 일관성

Task 상태와 속성을 변경하고 결과를 재조회한다.

여러 Task 간 Blocked By 관계를 생성하고, 차단 Task의 상태 변화에 따라 실행 가능 여부를 판별한다.

현재 Symphony에서 사용하는 차단 판단과 동일한 상태 조합을 적용해 결과를 비교한다.

존재하지 않는 Task 및 자기 자신을 대상으로 한 관계를 거부하는지 확인한다.

실패한 변경이 부분적으로 반영되지 않는지 확인한다.

### VR-6. 단순한 동시 쓰기 처리

동일 Task에 여러 Workpad 및 댓글 추가 요청을 동시에 수행한다.

각 성공 요청이 독립된 항목으로 정확히 한 번 기록되고, 누락되거나 덮어쓰이지 않는지 확인한다.

동시 속성 변경 후 저장 데이터의 일관성이 유지되는지도 확인한다.

SQLite의 일시적 쓰기 경합에서 정상적인 요청이 불필요하게 실패하지 않는지 검증한다.

### VR-7. Loop 인스턴스 독립성과 운영 단순성

격리된 두 Loop 인스턴스를 준비하고 각 인스턴스에서 서로 다른 Task를 저장한다.

각 인스턴스의 조회 결과에 다른 인스턴스의 작업이 나타나지 않는지 확인한다.

Loop 재시작 후 저장 데이터가 유지되는지 확인한다.

지원되는 런타임 업데이트 경로에서도 DB 파일이 보존되는지 확인한다.

추가 서버·포트·외부 인증 없이 저장소가 동작해야 통과한다.

### VR-8. 기존 실행 경로의 보존

현재 Notion 기반 Operator → Publisher → Symphony → Worker 경로의 관련 회귀 검증을 수행한다.

새 저장소가 초기화되지 않은 기존 환경에서도 현재 실행 경로가 정상 동작하는지 확인한다.

실제 외부 Notion 연동에 대한 E2E 실행이 가능한 환경에서는 대표 작업 발행부터 Worker 결과와 최종 상태까지 확인한다.

외부 E2E 환경을 사용할 수 없는 경우에는 기존 Adapter·Publisher·Operator 통합 테스트를 수행하고, 실제 Notion 기반 종단 실행이 검증되지 않았다는 한계를 명시한다.

## Verification Tools

- **Node.js 테스트 러너:** Local Task Store의 발행, 조회, 속성 변경, 기록 추가 및 실패 동작 검증
- **SQLite 실제 파일 테스트:** 트랜잭션, 영속성, 동시 쓰기 및 재연결 결과 확인
- **격리된 Loop 인스턴스:** 저장소 소유권, 인스턴스 간 격리, 재시작과 업데이트 검증
- **기존 Operator·Publisher 테스트:** 현재 Notion 작업 입력·발행 경로의 회귀 확인
- **Symphony Elixir 테스트:** 기존 Tracker Adapter 및 작업 실행 계약의 회귀 확인
- **기존 E2E Harness:** 사용 가능한 환경에서 실제 Notion 기반 작업 실행 경로의 보존 확인
- **Git Diff 및 정적 검사:** 보호 범위의 불필요한 변경과 의도하지 않은 의존성 추가 확인
