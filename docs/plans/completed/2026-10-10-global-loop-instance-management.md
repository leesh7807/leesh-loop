# 2026-10-10-global-loop-instance-management

## Objective

사용자가 어느 디렉터리에서든 전역 `leesh-loop` CLI를 통해 생성된 Loop 인스턴스들을 조회하고, 원하는 인스턴스를 시작하거나 종료할 수 있도록 한다.

`leesh-loop init`으로 생성한 인스턴스는 실행 여부와 관계없이 지속적으로 조회할 수 있어야 한다. 기존에 생성한 Loop도 일반적인 업데이트 또는 실행 과정에서 전역 관리 대상으로 편입할 수 있어야 한다.

## Intent

현재 각 Loop는 독립적인 디렉터리에서 `npm start`와 `npm stop`으로 실행 및 종료된다. 백그라운드 프로세스는 이미 터미널과 분리되어 실행되지만, 여러 Loop를 한곳에서 발견하고 관리하는 수단이 없다.

사용자는 `npm link`로 제공되는 기존 `leesh-loop` CLI에서 인스턴스 목록을 보고 선택적으로 시작하거나 종료하기를 원한다.

전역 명령은 새로운 프로세스 실행 모델을 도입하는 것이 아니라, 선택한 Loop 디렉터리에서 기존 `npm start` 또는 `npm stop`을 실행하는 인터페이스여야 한다.

실행하지 않는 Loop도 관리 대상에 남아 있어야 한다. 기존 Loop는 별도의 수동 등록 절차 없이 `update` 또는 `npm start`를 통해 등록될 수 있어야 한다.

## Verification Requirements

1. **인스턴스 등록**
   - `leesh-loop init`이 성공하면 생성된 독립 Loop가 사용자별 전역 레지스트리에 등록된다.
   - `leesh-loop update`와 `leesh-loop update --workflow`가 성공하면 해당 Loop가 등록되어 있어야 한다.
   - 기존에 생성된 미등록 Loop도 해당 디렉터리의 `npm start`를 통해 등록될 수 있다.
   - 동일한 Loop의 반복 등록은 중복 인스턴스를 만들지 않는다.
   - 서로 다른 Loop를 동시에 등록해도 등록 정보가 유실되지 않는다.
   - `init` 또는 `update` 자체가 실패하면 해당 명령으로 인한 신규 등록은 발생하지 않는다.
   - 원래 작업은 성공했지만 등록이 실패한 경우 두 결과를 구분하여 보고하고, 이후 등록을 재시도할 수 있다.
   - 등록 여부는 기존 `npm start` 및 `npm stop`의 실행 가능 여부를 제한하지 않는다.

2. **인스턴스 조회**
   - `leesh-loop list`는 현재 작업 디렉터리와 관계없이 등록된 모든 Loop를 조회한다.
   - 각 항목은 인스턴스를 구별할 수 있는 이름, 고유 ID, 경로 및 실행 상태를 제공한다.
   - 정상 실행 중인 인스턴스는 `Running`, 실행 중이지 않음이 확인된 인스턴스는 `Stopped`로 표시한다.
   - 실행 여부 또는 소유권을 확정할 수 없는 인스턴스는 `Unconfirmed`, 등록된 Loop 디렉터리가 사라진 경우에는 `Missing`으로 표시한다.
   - 한 인스턴스의 상태를 확인할 수 없어도 다른 인스턴스의 조회는 가능해야 한다.
   - 단순 조회는 Loop의 시작·종료, 등록 정보 삭제 또는 runtime state 정리를 수행하지 않는다.
   - 등록된 인스턴스가 없는 경우 정상적으로 빈 목록을 반환한다.

3. **전역 시작**
   - `leesh-loop start <instance>`는 선택한 Loop 디렉터리에서 `npm start`를 실행한다.
   - 해당 독립 Loop의 기존 시작 경로가 실제 실행을 담당한다.
   - 기존 설정 검증, readiness, 실행 중인 인스턴스 재사용 및 시작 실패 계약이 유지된다.
   - 시작 명령의 출력과 성공·실패 결과가 호출자에게 전달된다.
   - 실제 시작이 실패했거나 완료되지 않았다면 성공으로 보고하지 않는다.
   - CLI는 기존 시작 절차가 완료된 후 종료되며 장기 실행 서비스에 연결된 상태로 남지 않는다.

4. **전역 종료**
   - `leesh-loop stop <instance>`는 선택한 Loop 디렉터리에서 `npm stop`을 실행한다.
   - 해당 독립 Loop의 기존 종료 경로가 실제 종료를 담당한다.
   - 기존 PID 및 프로세스 시작 시점, Runtime ID, 프로세스 소유권, 종료 확인 계약이 유지된다.
   - 종료 실패 또는 종료 여부를 확정할 수 없는 경우 성공으로 보고하지 않는다.
   - 종료한 인스턴스의 전역 등록 정보는 유지된다.
   - 종료 후 실제 실행 상태를 다시 조회할 수 있으며 해당 인스턴스를 재시작할 수 있다.

5. **인스턴스 식별 및 격리**
   - 서로 다른 경로에 있는 동일한 이름의 Loop를 각각 등록할 수 있다.
   - 인스턴스 ID는 이름과 독립적으로 고유해야 하며, 같은 Loop를 반복 등록해도 유지된다.
   - 인스턴스 선택은 하나의 Loop로 명확하게 해석되어야 한다.
   - 이름이 중복되어 선택이 모호하면 임의의 인스턴스를 시작하거나 종료하지 않는다.
   - 등록된 경로가 없어지거나 다른 Loop를 가리키도록 변경된 경우 기존 등록 정보만 믿고 해당 대상을 실행하거나 종료하지 않는다.
   - 한 Loop의 시작·종료·등록 작업은 다른 Loop의 실행 및 등록 상태를 변경하지 않는다.
   - 전역 CLI는 등록된 Loop만 대상으로 하며 임의의 시스템 프로세스를 관리하지 않는다.

6. **기존 계약 유지**
   - `leesh-loop init`은 대상 저장소의 형제 디렉터리에 독립적인 Loop를 생성하며 대상 저장소를 변경하지 않는다.
   - 생성된 Loop는 원본 leesh-loop 소스 체크아웃에 의존하지 않고 실행할 수 있다.
   - `leesh-loop update`와 `leesh-loop update --workflow`의 기존 파일 관리 및 업데이트 계약은 유지된다.
   - `npm start`, `npm run start:fast`, `npm stop`의 기존 실행·종료 의미를 유지한다.
   - 전역 레지스트리는 인스턴스 발견을 담당하며, 기존 프로젝트별 runtime state 및 프로세스 소유권 판단을 대체하지 않는다.
   - 전역 CLI는 프로세스를 직접 실행·종료하는 새로운 관리 체계를 만들지 않는다.
   - Loop 프로세스 관리는 Notion 작업 State나 Workflow의 작업 진행 상태를 직접 변경하지 않는다.
   - 상주 관리자, OS 서비스 관리, 자동 시작 및 자동 재시작은 이번 범위에 포함하지 않는다.

## Definitions

- **Loop 인스턴스**: 독립적으로 실행할 수 있도록 생성된 Loop 디렉터리.
- **전역 CLI**: `npm link` 등으로 설치되어 작업 디렉터리와 관계없이 사용할 수 있는 `leesh-loop` 명령.
- **전역 레지스트리**: 사용자 계정에서 관리하는 Loop 인스턴스의 영구 등록 정보. 실제 실행 상태의 권위 있는 근거는 아니다.
- **인스턴스 ID**: 각 Loop를 안정적으로 구별하는 고유 식별자.
- **인스턴스 이름**: 사람이 구별하기 쉬운 표시 이름. 중복될 수 있다.
- **Loop 경로**: `project.toml`과 `package.json`이 존재하는 독립 Loop의 루트 경로.
- **Running**: 기존 runtime의 실행 및 소유권 검증을 통해 정상 실행 중임이 확인된 상태.
- **Stopped**: 해당 Loop가 실행 중이지 않음이 확인된 상태.
- **Unconfirmed**: 실행 상태나 소유권을 확정할 수 없는 상태.
- **Missing**: 등록된 Loop 경로가 존재하지 않는 상태.

## Decisions

### 1. CLI 인터페이스

기존 전역 CLI의 `init`, `update`, `update --workflow`를 유지하고 다음 명령을 추가한다.

```bash
leesh-loop list
leesh-loop start <instance>
leesh-loop stop <instance>
```

`<instance>`에는 인스턴스 ID 또는 유일하게 해석되는 인스턴스 이름을 사용한다.

이름이 중복되어 선택이 모호하면 해당 이름의 인스턴스 ID와 경로를 표시하고 명확한 선택을 요구한다.

`start`와 `stop`은 선택한 Loop 디렉터리를 작업 디렉터리로 지정하여 각각 `npm start`와 `npm stop`을 호출한다.

기존 npm 명령의 출력 및 종료 결과를 전달하며, 별도의 프로세스 실행·종료 로직을 만들지 않는다.

### 2. 등록 생명주기

다음 명령의 성공을 등록 진입점으로 사용한다.

| 명령 | 등록 동작 |
|---|---|
| `leesh-loop init` | 새로 생성된 Loop 등록 |
| `leesh-loop update` | 미등록 Loop 등록, 기존 등록 유지 |
| `leesh-loop update --workflow` | 미등록 Loop 등록, 기존 등록 유지 |
| `npm start` | 미등록 Loop 등록, 기존 등록 유지 |
| `npm stop` | 등록 유지 |
| `leesh-loop stop <instance>` | 등록 유지 |

등록은 기존 명령의 주된 작업과 구분한다.

`init` 또는 `update`의 본래 작업이 실패하면 신규 등록을 수행하지 않는다.

본래 작업은 완료됐지만 등록이 실패했다면 완료된 작업을 되돌리지 않는다. 명령의 출력에서 실제 완료 상태와 등록 실패를 구분하고, 전체 명령은 실패 상태를 반환한다.

`npm start`에서는 등록 실패가 기존 실행을 차단하거나 이미 시작된 runtime을 종료하지 않도록 한다. 등록 실패는 명확히 보고하고, 이후 `npm start` 또는 `update`에서 재등록할 수 있다.

기존에 이미 실행 중인 미등록 Loop도 로컬 `npm start`를 다시 호출했을 때 기존 재사용 동작을 유지하면서 등록할 수 있다.

### 3. 전역 레지스트리

사용자별 로컬 상태 영역을 사용한다.

Linux에서는 XDG 상태 디렉터리 규칙을 사용하며, 기본 저장 위치는 다음과 같다.

```text
~/.local/state/leesh-loop/
```

`XDG_STATE_HOME`이 설정되어 있으면 해당 경로를 따른다.

등록 정보에는 인스턴스 ID, 이름, Loop 경로 등 발견과 식별에 필요한 정보만 저장한다.

실행 상태를 레지스트리에 고정하여 저장하거나, 레지스트리의 PID를 종료 권한의 근거로 사용하지 않는다.

실제 실행 여부는 각 Loop의 runtime state 및 실행 중인 프로세스에 대한 기존 확인 결과에서 판단한다.

등록 정보를 변경할 때는 원자성과 동시 실행 일관성을 유지한다.

### 4. 인스턴스 정체성

인스턴스 이름의 기본값은 Loop 디렉터리 이름이다.

인스턴스 ID는 이름과 별개로 유지한다.

같은 디렉터리를 여러 번 등록해도 기존 인스턴스를 재사용한다.

Loop 디렉터리를 이동하거나 복사한 경우 경로만으로 기존 인스턴스라고 가정하지 않는다. 등록된 식별 정보와 실제 Loop 정체성을 확인하여 충돌 또는 불일치를 명확히 처리한다.

다른 Loop로 바뀐 경로를 기존 인스턴스로 자동 재연결하지 않는다.

이번 범위에서 등록 정보의 삭제나 이동을 위한 별도 관리 명령은 추가하지 않는다.

### 5. 상태 판정 및 오류

`list`는 등록된 각 Loop의 현재 상태를 독립적으로 확인한다.

실행 중임을 확인할 수 있는 경우에만 `Running`, 실행하지 않음이 확인된 경우에만 `Stopped`로 판단한다.

판단 근거가 충분하지 않으면 `Unconfirmed`를 표시한다.

Loop 경로가 존재하지 않으면 `Missing`으로 표시한다.

`list`는 기존 runtime state를 복구하거나 정리하는 명령이 아니다.

전역 `start`와 `stop`은 대상 인스턴스의 정체성과 경로를 확인한 다음 기존 npm 명령을 실행한다.

하위 명령 실패, 등록 정보 오류, 인스턴스 선택 오류를 성공으로 바꾸지 않는다.

### 6. 책임 및 보호 범위

전역 CLI가 담당하는 책임은 다음과 같다.

- Loop 등록과 발견
- 인스턴스 식별 및 선택
- 등록된 Loop의 상태 조회
- 기존 npm 시작·종료 명령 위임

개별 Loop가 계속 담당하는 책임은 다음과 같다.

- Runtime 생성 및 소유권 관리
- Readiness
- Symphony 및 Operator UI 실행
- Runtime 종료와 종료 검증
- Project 설정과 환경 관리

다음 영역은 보호한다.

- Symphony의 dispatch 및 worker 실행
- Publisher 및 Notion 데이터 계약
- `project.toml`, `.env`, `WORKFLOW.md`의 기존 의미
- 독립 Loop 생성 및 runtime/workflow 업데이트 경계
- E2E harness의 실행 및 정리 책임

이번 목표와 무관한 변경은 별도 계획으로 분리한다.

파일, 모듈, 타입 및 주요 함수 이름은 현재 책임과 역할을 드러내도록 한다. 아직 존재하지 않는 추상적인 관리 계층을 전제로 이름을 붙이지 않는다.

## Planned Units

### Unit 1. Loop 등록과 전역 조회

독립 Loop의 등록 정보를 지속적으로 관리하고, 전역 CLI에서 등록된 모든 Loop와 실제 실행 상태를 확인할 수 있도록 한다.

`init`, `update`, `update --workflow`, `npm start`를 등록 진입점으로 연결한다.

중복 등록, 식별자 충돌, 동시 등록, 등록 실패, 미실행 인스턴스, 누락된 경로와 불확실한 실행 상태를 포함한다.

**완료 결과:** 신규 및 기존 Loop가 일반적인 생성·업데이트·실행 과정을 통해 전역 등록되고, 실행 여부와 관계없이 조회된다.

### Unit 2. 등록된 Loop의 전역 시작·종료

등록된 인스턴스를 명확하게 선택하여 해당 디렉터리의 기존 `npm start` 또는 `npm stop`을 호출한다.

기존 시작·종료 계약과 실행 결과 전달, 잘못된 대상 선택 방지 및 서로 다른 인스턴스 사이의 격리를 포함한다.

**완료 결과:** 사용자가 어느 디렉터리에서든 특정 Loop를 시작하거나 종료하고 실제 실행 상태 변화를 확인할 수 있다.

## Verification

### 1. 등록 경로

임시 Git 저장소에서 실제 `leesh-loop init`을 실행하여 독립 Loop를 생성한다.

생성 직후 등록 정보와 `leesh-loop list` 출력을 확인한다.

기존에 생성된 미등록 Loop를 별도로 준비하고 다음 각각의 등록 경로를 검증한다.

- `leesh-loop update`
- `leesh-loop update --workflow`
- `npm start`

각 명령 이후 동일한 Loop가 전역 목록에 나타나는지 확인한다.

반복 등록 시 인스턴스 ID가 유지되고 목록 항목 수가 증가하지 않아야 한다.

서로 다른 Loop의 동시 등록을 실행하고, 모든 등록 정보가 유지되는지 확인한다.

원래 작업 실패와 등록 실패를 각각 발생시켜 최종 상태 및 오류 보고가 계약과 일치하는지 확인한다.

### 2. 조회 및 실행 상태

등록된 여러 Loop에 대해 실행하지 않은 상태, 실행 중인 상태, 종료된 상태를 조회한다.

서로 다른 작업 디렉터리에서 동일한 등록 목록을 확인한다.

다음 결과를 각각 검증한다.

- 실행하지 않은 Loop → `Stopped`
- 정상 실행 중인 Loop → `Running`
- 소유권 또는 실행 상태 확인 불가 → `Unconfirmed`
- 등록된 디렉터리 삭제 → `Missing`
- 등록 항목 없음 → 빈 목록

조회 전후 프로세스 및 runtime state를 비교하여 `list`가 실행이나 종료 및 상태 정리를 수행하지 않았음을 확인한다.

### 3. 전역 시작

실제 생성된 독립 Loop를 등록한 후 전역 CLI에서 시작한다.

```text
leesh-loop list
  → Stopped

leesh-loop start <id>
  → 기존 npm start 실행

실제 runtime 확인
  → 정상 실행

leesh-loop list
  → Running
```

CLI 성공 여부뿐 아니라 실제 runtime identity 및 readiness 확인을 통해 실행 결과를 검증한다.

이미 실행 중인 Loop를 다시 시작해 기존 재사용 동작을 확인한다.

설정 오류나 readiness 실패가 전역 CLI에서도 실패로 전달되는지 확인한다.

### 4. 전역 종료

전역 CLI를 통해 실행 중인 Loop를 종료한다.

```text
leesh-loop stop <id>
  → 기존 npm stop 실행

runtime 및 Operator UI 종료 확인
  → 종료됨

leesh-loop list
  → Stopped
```

프로세스 종료와 runtime identity 확인 결과가 일치해야 한다.

종료 후에도 등록 정보와 인스턴스 ID가 유지되는지 확인한다.

같은 인스턴스를 다시 시작하여 정상적으로 `Running`으로 돌아가는지 확인한다.

프로세스 정체성 불일치 또는 종료 확인 실패 상황에서는 전역 CLI가 성공으로 보고하지 않는지 확인한다.

### 5. 식별 및 격리

이름이 같은 서로 다른 Loop 두 개를 등록한다.

이름만으로 시작·종료하려 하면 모호성 오류가 발생하고, 인스턴스 ID로 선택하면 정확한 Loop 하나에만 명령이 적용되어야 한다.

한 Loop의 시작·종료 및 등록 작업 중 다른 Loop의 실행 상태와 등록 정보가 유지되는지 확인한다.

등록된 경로를 삭제하거나 다른 Loop로 교체한 뒤, 기존 등록 기록을 통한 잘못된 실행·종료가 차단되는지 확인한다.

### 6. 기존 계약 회귀

다음 명령의 기존 동작을 확인한다.

```bash
leesh-loop init
leesh-loop update
leesh-loop update --workflow
npm start
npm run start:fast
npm stop
```

특히 생성된 독립 Loop를 원본 소스 체크아웃 없이 실행하고 종료할 수 있는지 확인한다.

기존 repository 테스트 및 관련 통합 테스트를 실행한다.

Project 설정, readiness, runtime 소유권, 관리 파일 업데이트 경계에 기존 계약과 다른 영향이 없는지 확인한다.

### 7. 통합 검증 범위

전역 CLI에서 실제 독립 Loop를 시작하고, runtime을 확인한 후 종료하는 전체 흐름을 최소 한 번 검증한다.

검증 환경에 필요한 외부 의존성이 없다면 실제 시작·종료 성공을 확인했다고 보고하지 않는다.

가능한 범위에서 CLI 위임, 등록, 오류 전달 및 상태 판정 검증을 수행하고, 실제 runtime 통합 검증에서 확인하지 못한 부분을 명시한다.

## Verification Tools

- **Node.js test runner (`node --test`)**: 등록, 식별, 동시성, 오류 처리, 상태 판정 및 회귀 검증.
- **실제 전역 CLI (`npm link`)**: 명령 진입점, 디렉터리 독립성, npm 실행 위임 및 종료 코드 확인.
- **임시 Git 저장소 및 `leesh-loop init` 결과물**: 신규 Loop 생성과 등록 검증.
- **기존 Loop의 `update` 실행**: 미등록 인스턴스의 자동 등록과 기존 업데이트 계약 검증.
- **실제 Loop 시작·종료 통합 실행**: `start`와 `stop`의 외부 효과 및 실행 상태 전환.
- **Runtime state와 실행 중인 프로세스 및 런타임 API**: 실행 상태, PID, Runtime ID, 소유권과 종료 결과 확인.
- **기존 repository 테스트 및 E2E harness**: 독립 실행, readiness, 업데이트 및 기존 운영 계약의 회귀 검증.
