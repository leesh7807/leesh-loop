# 2026-10-23-operator-ui-design-and-publication-improvement

## Objective

Leesh Loop의 Operator UI를 무채색 기반으로 전반적으로 개선하여 높은 가독성, 명확한 정보 위계, 세련되고 일관된 시각적 완성도와 편리한 작업 경험을 제공한다.

현재 UI의 기능적 불편함을 해소하는 것과 별개로, 전체적인 디자인의 난잡함과 미적 완성도 부족을 독립적인 개선 대상으로 삼는다.

Task의 현재 State를 쉽게 인식하고 변경할 수 있도록 하며, Accepted Plan 발행에서는 불필요한 제목 형식 및 중복 제한을 제거하고 단순하고 예측 가능한 동작을 제공한다.

## Intent

현재 Operator UI는 무채색과 절제된 선·박스를 통해 단순한 디자인을 지향하지만, 실제 결과물은 충분히 읽기 쉽거나 보기 좋지 않다.

이는 특정 기능의 사용성 문제만은 아니다. 화면의 전체적인 구성, 정보 밀도, 타이포그래피, 여백, 정렬, 경계와 강조의 사용 방식에서 디자인이 난잡하게 느껴지는 문제도 존재한다. 이러한 문제를 개별 불편 사항의 수정 결과로 간접적으로 해결하려 하지 않고, 디자인 조사와 재구성의 직접적인 대상으로 삼는다.

무채색은 유지하되 시각적 표현을 지나치게 제한할 필요는 없다. 기존 스타일을 보존하거나 특정 디자인 요소를 제거하는 것보다 최종적인 가독성과 미적 완성도를 우선한다. 다른 우수한 인터페이스의 사례를 조사하고, 실제 결과물을 비교·평가하며 개선한다.

구체적으로 확인된 사용성 문제는 다음과 같다.

- State 변경 컨트롤이 Task 상세의 마지막에 있어 긴 내용을 읽는 동안 접근하기 어렵다.
- State 변경 후 저장된 결과를 직관적으로 인식하기 어렵다. 결과 메시지가 변경 컨트롤과 떨어져 있고, 구분선으로 감싼 표현도 적절하지 않다.
- Plan 발행 후 화면 상태에 이전 Plan이 남아 있어 다음 발행을 시작할 때 불필요한 정리가 필요하다.
- Plan 제목에 Markdown H1을 필수로 요구한다.
- Plan 원문 기반 식별자를 발행 멱등성에 사용하여 동일한 Plan을 별도 Task로 반복 발행할 수 없다.

Plan의 제목은 내용을 식별하기 위한 편의적 표시일 뿐, 구조를 분석하거나 발행을 제한하기 위한 규칙일 필요는 없다. 동일한 내용을 다시 발행하는 것 역시 사용자에게 허용되는 일반적인 행동으로 취급한다.

전체 개선은 KISS, YAGNI, DRY 원칙에 따라 필요한 결과를 가장 단순한 구조로 달성하는 방향을 따른다.

## Verification Requirements

### 1. 시각적 품질과 가독성

- Operator UI 전체에서 무채색 디자인을 유지한다.
- 화면의 전반적인 조형적 완성도, 균형, 일관성과 정돈된 인상이 기존보다 개선되어야 한다.
- Task 목록, 상세, Plan 발행 화면이 시각적으로 자연스럽게 연결되어야 한다.
- 제목, State, 주요 행동, 본문, 보조 정보가 직관적으로 구별되어야 한다.
- 타이포그래피, 여백, 정렬, 대비, 정보 밀도와 배치가 내용의 역할과 중요도에 부합해야 한다.
- 선, 면, 박스, 경계, 강조의 중복이나 불필요한 반복이 시각적 혼잡을 일으키지 않아야 한다.
- 긴 텍스트, 많은 Task, 여러 Blocked By, 긴 Workpad와 댓글에서도 핵심 정보를 찾고 읽기 쉬워야 한다.
- 넓은 화면과 좁은 화면에서 정보 위계와 조작 가능성이 유지되어야 한다.
- 추가하는 폰트 및 관련 에셋은 배포·재배포가 허용되는 라이선스를 사용해야 하며, 폰트 로드 실패 시에도 읽기 쉬운 대체 표현을 제공해야 한다.
- 기능적으로 동작한다는 사실만으로 디자인 개선을 완료한 것으로 판단하지 않는다. 실제 렌더링 결과에 대한 별도의 시각적 평가가 이루어져야 한다.

### 2. State 변경 접근성과 피드백

- Task 상세의 어느 부분을 읽는 중이더라도 State 변경 컨트롤에 쉽게 접근할 수 있어야 한다.
- 현재 저장된 State와 사용자가 선택한 State를 혼동하지 않아야 한다.
- State 저장 중, 성공, 실패가 시각적으로 명확하게 구별되어야 한다.
- State 변경 결과는 해당 조작 컨트롤 근처에 표시되어야 한다.
- 사용자는 결과를 확인하기 위해 다른 화면 영역을 찾아 이동할 필요가 없어야 한다.
- 저장 성공 후 상세와 목록은 실제 저장된 State를 반영해야 한다.
- 저장 실패 시 성공으로 오인하지 않아야 하며, 사용자가 선택한 값을 불필요하게 잃지 않고 재시도할 수 있어야 한다.
- 자동 갱신이나 Task 전환으로 인해 오래된 결과 메시지가 현재 상태를 잘못 설명하지 않아야 한다.
- 좁은 화면과 키보드 조작에서도 동일한 행동과 피드백에 접근할 수 있어야 한다.

### 3. Plan 제목과 반복 발행

- 비어 있지 않은 Accepted Plan은 H1이나 특정 Markdown 구조 없이 발행할 수 있어야 한다.
- 제목은 Plan 시작 부분의 정해진 길이만큼을 사용하는 단순한 규칙으로 생성한다.
- 제목 생성에 Markdown 파싱, 문장 선택 또는 내용의 의미를 분석하는 조건을 도입하지 않는다.
- 동일한 제목이 발생하면 기존 제목과 구별되는 숫자 접미사를 자동으로 부여한다.
- **동일한 Accepted Plan을 여러 번 발행할 수 있어야 하며, 각 발행은 별개의 Task를 생성해야 한다.**
- Plan 원문이 같다는 이유로 발행을 거부하거나 기존 Task를 반환하지 않는다.
- Task의 식별자는 원문의 동일성에 종속되지 않으며, 서로 다른 Task는 고유한 식별자를 가진다.
- 동시 발행 상황에서도 생성된 Task와 제목이 충돌하거나 유실되지 않아야 한다.
- 제목을 구별하기 위한 접미사는 Accepted Plan 원문을 수정하지 않아야 한다.
- 발행이 실패하면 새로운 Task의 성공적인 생성을 보고해서는 안 된다.

### 4. 발행 초안 관리

- 발행 성공 후 Plan 입력 내용, State 선택, Blocked By 선택이 초기화되어야 한다.
- 발행 화면으로 다시 돌아오거나 새로고침해도 성공적으로 발행한 이전 초안이 복원되지 않아야 한다.
- 발행 실패나 결과가 확인되지 않은 상황에서는 입력 내용을 임의로 삭제하지 않아야 한다.
- 발행 중 반복적인 버튼 조작이 의도하지 않은 다중 요청을 일으키지 않아야 한다.
- 발행된 Task 상세에서는 원본 Accepted Plan과 실제 발행 결과를 확인할 수 있어야 한다.

### 5. 기존 동작과 데이터 보존

- Task 조회, Human Review 우선순위, 목록 탐색, Blocked By 변경, 댓글 작성, Workpad와 Accepted Plan 열람이 유지되어야 한다.
- State 변경은 기존 Local Task Store와 Workflow의 의미를 따른다.
- 기존 Task의 식별자, 저장된 제목, Accepted Plan과 실행 기록은 변경되지 않아야 한다.
- Symphony, Worker, GitHub 연동 및 기존 실행 계약이 UI 개선으로 인해 퇴행하지 않아야 한다.

## Definitions

- **Operator UI:** Task의 발행, 조회와 관리를 담당하는 로컬 웹 인터페이스.
- **Task:** Accepted Plan, 식별자, State, Blocked By 및 실행 기록을 가지는 작업 단위.
- **Accepted Plan:** 발행 시 Task에 귀속되는 불변 Plan 원문.
- **기본 제목:** Accepted Plan의 앞부분에서 일관된 규칙으로 생성한 문자열.
- **표시 제목:** 기본 제목에 필요한 경우 숫자 접미사를 붙여 Task에 저장하는 제목.
- **발행 요청:** 새 Task를 생성하기 위한 사용자 또는 발행 진입점의 개별 요청.
- **발행 초안:** 아직 발행되지 않은 Plan 내용, State와 Blocked By 선택.
- **Local Publisher:** Accepted Plan의 제목과 식별자 생성 및 발행을 담당하는 구성 요소.
- **Local Task Store:** Loop별 SQLite 기반 Task 권위 저장소.
- **Workflow:** State의 의미와 Worker의 작업 진행 규칙을 정의하는 실행 계약.
- **무채색 디자인:** 흰색·검정·회색의 명도 차이를 사용하는 시각적 표현.

## Decisions

### 1. 디자인 조사와 개선 방향

`docs/DESIGN.md`의 사용자 작업 중심 원칙을 유지하되, 현재 화면의 스타일을 정답으로 가정하지 않는다.

개선 방향을 결정하기 위해 현재 UI를 시각적·기능적 관점에서 각각 평가한다.

시각적 조사에서는 다음을 다룬다.

- 전체 레이아웃의 비례와 시각적 균형
- 타이포그래피의 품질과 크기·굵기·행간의 관계
- 요소 사이 여백과 반복 간격이 만드는 시각적 리듬
- 텍스트 및 컨트롤의 정렬과 그룹화
- 정보 밀도의 배분과 시선의 흐름
- 선·면·박스·경계의 사용 목적과 중복 여부
- 주요 행동과 보조 행동 사이의 강조 수준
- 페이지 전체의 일관성과 미적 완성도

실제 사용성이 뛰어나고 시각적 완성도가 높은 인터페이스를 조사한다. 무채색 UI, 텍스트 중심 작업 도구, 개발자 도구와 관리 화면 등을 참고 대상으로 삼되, 특정 제품의 외형을 그대로 복제하지 않는다.

레퍼런스의 구체적인 장점과 현재 Operator에 적용할 수 있는 원리를 구별한다. 조사 결과가 실제 시각적 개선에 반영되어야 하며, 레퍼런스 수집만으로 조사를 완료하지 않는다.

### 2. 시각적 표현 수단

무채색을 유지한다는 조건 외에는 특정 디자인 표현을 일률적으로 금지하지 않는다.

타이포그래피, 대비, 크기, 정렬, 간격, 면, 선, 경계, 음영 등은 화면의 품질을 높이는 범위에서 사용할 수 있다.

장식 요소가 적은 것과 디자인이 좋은 것은 별개로 판단한다. 요소를 줄이는 것이 항상 정답은 아니며, 새로운 표현을 추가하는 것도 그 자체로 개선을 뜻하지 않는다.

폰트는 배포 가능한 라이선스라면 추가할 수 있다. 한국어와 영문의 실제 렌더링, 글꼴의 성격, 본문 가독성, 배포 비용과 대체 폰트를 함께 고려한다.

별도의 범용 UI 프레임워크나 디자인 시스템 구축은 목표로 삼지 않는다.

### 3. State 변경 컨트롤

State 변경을 Task 상세의 주요 행동으로 배치한다.

Task 제목과 현재 State의 문맥에서 바로 발견할 수 있도록 구성하고, 긴 상세 내용을 스크롤하는 중에도 접근할 수 있게 한다.

기본 방향은 Sticky 또는 이에 준하는 접근성 있는 배치다. 다만 실제 구현은 화면의 공간과 조작 편의성에 따라 결정하며, 고정 컨트롤이 본문을 가리거나 좁은 화면을 불필요하게 차지해서는 안 된다.

기존의 명시적 State 저장과 서버 응답을 통한 확정 방식을 유지한다.

Human Review에서 댓글을 읽거나 작성한 뒤 다음 State를 선택하는 작업 흐름 역시 보존한다.

### 4. State 변경 결과 표현

결과 피드백은 State 변경 컨트롤과 같은 시각적 문맥에 둔다.

현재 State, 선택 중인 State, 저장 중 표시와 확정 결과는 의미에 따라 구별한다.

성공 시 실제 서버 응답으로 확정된 State를 표시하고, 실패 시 오류를 해당 조작 위치에서 확인할 수 있도록 한다.

현재의 두 구분선 사이에 메시지를 배치하는 방식은 유지할 필요가 없다. 알림의 위치, 형태와 강조 수준을 화면 전체의 디자인 방향과 함께 개선한다.

Blocked By 및 댓글 저장 결과도 가능하면 해당 행동과 연결되도록 정리하되, 새로운 공통 알림 시스템 구축을 목표로 삼지 않는다.

### 5. Plan 제목 생성

H1과 Markdown 문법에 관한 제목 검증을 제거한다.

기본 제목은 다음의 단일 규칙으로 생성한다.

> Plan 원문의 앞뒤 공백을 제거하고, 연속된 공백·줄바꿈을 하나의 공백으로 정리한 다음, 앞 80자를 기본 제목으로 사용한다.

다른 제목 후보를 찾거나 Markdown 구조를 분석하지 않는다.

예시:

| Plan 시작 내용 | 기본 제목 |
|---|---|
| `# 로그인 기능 개선` | `# 로그인 기능 개선` |
| `로그인 기능의 오류를 수정한다.` | `로그인 기능의 오류를 수정한다.` |
| `## Objective` 다음 줄에 `로그인 오류 해결` | `## Objective 로그인 오류 해결` |

원문의 Markdown 기호가 제목에 남는 것도 허용한다.

80자 이후 내용을 기반으로 문장 경계를 조정하거나 새로운 제목을 선택하지 않는다.

내용 전체가 공백인 경우에는 발행을 허용하지 않는다. 그 외 제목 추출을 위한 별도의 형식 검증이나 예외 규칙은 도입하지 않는다.

이 규칙은 Operator UI뿐 아니라 동일 Local Publisher를 이용하는 발행 진입점에 일관되게 적용한다.

Repository Plan의 `date-summary` 명명 규칙은 변경하지 않는다.

### 6. 중복 제목 처리

서로 다른 Task의 기본 제목이 같을 수 있다.

표시 제목을 결정할 때 이미 사용 중인 제목과 충돌하면 다음과 같이 숫자 접미사를 붙인다.

- `로그인 기능 개선`
- `로그인 기능 개선 (1)`
- `로그인 기능 개선 (2)`

사용하지 않은 가장 작은 양의 정수를 선택한다.

동일한 Plan을 다시 발행하는 경우에도 같은 규칙을 적용한다.

제목 충돌 처리는 Local Store의 권위 데이터에 기반해 발행과 원자적으로 이루어져야 한다.

기존 Task의 제목을 소급해서 변경하거나 Accepted Plan 원문에 접미사를 추가하지 않는다.

### 7. 동일 Plan 반복 발행

Plan 원문의 동일성은 발행 제한 조건으로 사용하지 않는다.

각 발행 요청은 독립적인 새 Task를 생성한다. 식별자는 요청마다 고유하게 부여하며, 기존 원문 해시 기반의 Task 재사용 동작을 제거한다.

현재 Local Task Store가 제공하는 동일 발행키의 멱등성 계약을 전역적으로 제거할 필요는 없다. Local Publisher가 새로운 발행 요청마다 독립적인 발행키를 부여하도록 하여 사용자 수준의 반복 발행을 허용한다.

동일 Plan의 존재 여부를 확인하거나 경고하는 기능은 이번 계획에 포함하지 않는다. 필요성이 확인되면 별도로 판단한다.

반복 발행을 허용하므로 응답을 확인하지 못한 요청을 사용자가 다시 제출하면 별도 Task가 생성될 수 있다. 이는 이번 변경의 의도된 발행 의미이며, UI는 요청의 확정 여부를 사실대로 표시해야 한다.

### 8. 발행 후 초안 초기화

발행 성공이 확인되면 React 화면 상태와 브라우저에 보존된 초안을 모두 초기화한다.

다시 발행 화면에 진입하면 빈 Plan, 기본 State, 비어 있는 Blocked By 선택에서 시작한다.

발행 실패 또는 응답이 확인되지 않은 경우에는 초안을 보존한다. 성공 여부를 확인하지 못했다는 이유만으로 입력을 삭제하거나 새 Task가 생성되지 않았다고 단정하지 않는다.

발행 중에는 중복 제출 조작을 방지하되, 이전에 발행한 내용과 동일하다는 이유로 새로운 발행을 제한하지 않는다.

### 9. 보호 범위와 명명

Local Task Store는 권위 저장소로 유지한다.

다음 책임과 동작은 보호한다.

- Workflow의 State 의미와 Worker 실행 정책
- Accepted Plan의 불변성
- 기존 Task 및 기록의 보존
- Blocked By와 댓글의 저장 의미
- Symphony와 Worker의 실행 연동
- GitHub PR 및 외부 서비스 계약
- Operator의 기존 작업 탐색과 Human Review 기능

발행 식별자 생성 및 제목 충돌 처리에 필요한 변경만 Publisher와 Store에 적용한다.

파일, 모듈, 타입, 주요 함수의 명칭은 실제 책임을 드러내고 장기적으로 의미를 유지해야 한다. 이번 변경에만 유효한 임시 명칭이나 불필요한 범용 추상화를 피한다.

간단한 제목 생성, 중복 제목 구분, 동일 Plan 반복 발행을 구현한다.

## Verification

### 1. 디자인 조사 및 시각적 평가

기존 Operator 화면의 주요 문제를 실제 렌더링을 기준으로 확인한다.

관련 UI 레퍼런스를 조사하여 적용 가능한 타이포그래피, 정보 위계, 간격, 레이아웃과 시각적 표현 원리를 기록한다.

개선 전후의 실제 화면을 비교하며 다음을 평가한다.

- 정보가 시각적으로 자연스럽게 묶이는가?
- Task 제목, State와 주요 행동이 먼저 발견되는가?
- 타이포그래피와 여백에 일관된 리듬이 있는가?
- 불필요한 선·경계·강조가 혼잡을 만들지 않는가?
- 화면의 비례, 정보 밀도와 시각적 균형이 자연스러운가?
- 개별 구성 요소가 아닌 전체 화면으로 보았을 때 세련되고 정돈된 인상을 주는가?
- 참고한 디자인 원리가 실제 개선으로 이어졌는가?

기능 사용성 검증과 시각적 품질 검토를 별도로 수행한다. 주요 시각적 문제가 그대로 남아 있다면 기능 테스트에 통과해도 디자인 작업을 완료한 것으로 판단하지 않는다.

### 2. 대표 화면 검증

실제 Operator를 다음 조건에서 확인한다.

- 빈 Task 목록과 Plan 발행 화면
- 여러 State를 포함한 다수 Task 목록
- Human Review와 진행 중 Task가 함께 있는 화면
- 긴 제목 및 여러 Blocked By를 가진 Task
- 긴 Accepted Plan, Workpad와 댓글이 있는 상세 화면
- State 저장 중, 성공 및 실패 화면
- 넓은 데스크톱과 모바일을 포함한 좁은 화면

화면을 실제로 조작하면서 정보 탐색, 스크롤, 읽기와 입력을 평가한다.

최종 캡처를 `docs/ui-evidence/`에 보존하여 화면의 시각적 완성도를 검토할 수 있도록 한다.

### 3. State 변경 검증

긴 상세를 스크롤한 상태에서 State 변경 컨트롤을 발견하고 조작할 수 있는지 확인한다.

State 저장 후 다음을 확인한다.

- 현재 값과 선택 값이 구별된다.
- 저장 중과 결과가 컨트롤 근처에 표시된다.
- 성공 응답 이후 목록과 상세가 실제 State를 표시한다.
- Local Store 재조회 결과가 화면에 표시된 결과와 일치한다.
- 실패 시 사용자 선택이 보존되고 재시도가 가능하다.
- 자동 갱신이나 Task 전환 후 잘못된 오래된 피드백이 남지 않는다.
- 좁은 화면에서도 컨트롤이 내용을 가리지 않으며 접근 가능하다.

### 4. Plan 제목 및 반복 발행 검증

실제 Local Publisher와 Operator API를 사용하여 다음을 확인한다.

- H1이 있는 Plan
- H1 없이 일반 문장으로 시작하는 Plan
- 공백과 여러 줄의 Markdown을 포함한 Plan
- 80자보다 긴 Plan
- 내용이 비어 있거나 공백만 있는 Plan
- 동일한 기본 제목을 가진 서로 다른 Plan
- 완전히 동일한 Plan의 반복 발행
- 같은 기본 제목을 가진 여러 발행 요청의 동시 실행

각 발행 결과를 Local Store에서 독립적으로 확인한다.

동일 원문 반복 발행에서는 각각 서로 다른 Task ID와 식별자가 생성되어야 한다. 제목 접미사는 충돌 없이 부여되어야 한다.

발행된 Accepted Plan 원문이 입력과 일치하고 변경되지 않았음을 확인한다.

기존 발행키 기반 Store 동작도 필요한 범위에서 회귀 검증한다.

### 5. 발행 초안 검증

실제 브라우저에서 Plan, State, Blocked By를 입력하고 발행한다.

성공 시 발행된 Task를 확인한 후 새 발행 화면으로 돌아와 입력이 초기화되었는지 확인한다. 새로고침 후에도 이전 초안이 복원되지 않아야 한다.

실패 및 응답을 확인하지 못한 상황에서는 초안이 보존되는지 확인한다.

동일 Plan을 다시 입력해 별도 Task로 발행할 수 있는지도 검증한다.

### 6. 기존 기능 회귀 검증

Task 탐색, Human Review, Blocked By, 댓글, Workpad 및 Accepted Plan 조회를 실제 Operator 경로에서 확인한다.

State 변경과 댓글 입력이 Local Store에 반영되고, 기존 Symphony 및 Worker 연동 의미가 유지되는지 대표적인 통합 경로에서 확인한다.

기존 Task 데이터가 변경 없이 조회되는지 검증한다.

## Verification Tools

- **실제 브라우저:** 디자인 완성도, 정보 위계, 스크롤, Sticky 컨트롤, 조작 결과와 반응형 레이아웃 검증.
- **UI 레퍼런스 조사 및 화면 비교:** 미적 문제 진단, 개선 방향 도출 및 최종 시각적 품질 평가.
- **Node 테스트:** 제목 생성, 반복 발행, 제목 충돌, 동시 발행과 실패 처리 검증.
- **Operator UI 테스트 및 Vite 빌드:** 사용자 입력 상태, 초안 생명주기, UI 상호작용과 프런트엔드 빌드 검증.
- **Local Operator 서버와 Publisher:** 실제 HTTP 발행 및 Task 변경 경로 검증.
- **SQLite 독립 재조회:** Task 식별자, 표시 제목, State, 불변 Accepted Plan과 저장 결과 확인.
- **내부 Smoke Run:** Operator, Local Store, Symphony 및 통제된 Worker를 통한 대표적인 통합 흐름 검증.
- **화면 캡처:** 개선 전후와 화면 크기별 디자인 결과를 비교하고 리뷰 증거로 보존.
- **폰트 라이선스 및 배포 파일 검토:** 신규 폰트의 사용·재배포 조건과 대체 폰트 동작 확인.
