# 2026-10-27-manager-cli-experience-redesign

## Objective

leesh-loop의 Manager UI와 CLI를 사용자의 실제 작업 흐름을 중심으로 재설계한다.

사용자는 leesh-loop를 실행하고, Git 프로젝트를 등록·선택하고, Loop와 Task 작업을 진행하며, 프로젝트를 전환하고, 필요한 관리 기능을 사용한 뒤, 사용을 종료하거나 다시 진입하는 과정을 자연스럽고 일관되게 수행할 수 있어야 한다.

기존의 안정적인 실행·데이터·보안 계약을 유지하면서, 내부 구현에 대한 이해나 불필요한 탐색 없이 주요 기능을 사용할 수 있는 경험을 만든다.

## Intent

PR #120은 여러 Git 저장소를 하나의 중앙 Manager로 관리하도록 구조를 전환했고, PR #121은 생명주기와 복구 문제를 개선했다. 그러나 현재 사용자 경험에는 구조적인 문제가 남아 있다.

프로젝트 등록·선택, Loop 실행, Task 작업, Runtime·Workflow 관리와 진단 기능이 하나의 화면에 혼재되어 있다. 중요도와 사용 빈도가 다른 기능에 접기를 반복적으로 사용하면서 정보 구조와 탐색의 문제를 해결하려는 경향이 있다. 프로젝트를 선택하고 작업에 집중하는 경험이 명확하지 않다.

CLI 역시 기능은 제공하지만 프로젝트 이름보다 내부 Instance ID를 요구하거나, Manager Service와 Loop Process의 차이를 사용자가 이해해야 하는 순간이 있다. 브라우저를 닫는 것과 Manager를 종료하는 것의 의미가 불분명하고, 새 프로젝트 등록과 실패 후 복구에도 불필요한 마찰이 있다.

로컬 Manager의 엄격한 Host 검증과 인증 토큰은 외부 웹사이트가 로컬 실행 권한을 악용하는 위험을 방어한다. 이 보안 목적은 유효하지만, `localhost` 접근 차단, `file://` 기반 브라우저 부트스트랩, Runtime 변경에 따른 토큰 무효화 및 기존 탭의 인증 실패 처리까지 현재 방식 그대로 유지해야 하는 것은 아니다. 필요한 보안 경계를 지키면서 접근과 재진입 경험을 개선해야 한다.

시각적으로는 무채색을 기본 언어로 사용하고, 실제 주의가 필요한 상황을 위한 단일 경고색만 허용한다. 화면의 구조와 정보 위계를 색이나 과도한 경계선·접기로 대신하지 않는다. 색상과 접기 사용의 철학 및 구체적인 규칙을 지속 가능한 디자인 문서에 남긴다.

이번 작업은 기존 UI를 정돈하거나 기능을 추가하는 데 목적이 있지 않다. 사용자에게 드러나는 개념, 작업 순서, 정보 위계, 탐색 및 상호작용을 재평가하여 하나의 일관된 제품 경험으로 만드는 것이 목적이다.

기존 Manager/Operator 구분과 현재 페이지 구조는 평가 대상이지 보존해야 할 디자인 계약이 아니다. 반면 이미 검증된 Loop 실행, Worker, Task Store, Runtime 보호 및 안전한 복구의 의미는 유지한다.

PR #121에서 제작된 일부 시각적 증거는 실제 브라우저 화면을 캡처한 것이 아니라 수동으로 재구성한 SVG였으며, 실제 실행 화면과 상당한 불일치가 확인되었다. 이로 인해 해당 자료에 표현된 화면 구성과 정보 위계를 실제 사용자 경험으로 판단할 수 없었다. 따라서 이러한 자료를 현재 UI의 시각적 증거로 사용하지 않는다. 이는 기존 테스트, API 검증, 프로세스 관찰이나 실제 브라우저 캡처까지 무효화한다는 의미가 아니다. 각 증거가 실제로 입증하는 대상과 구현 버전을 구별하여 평가한다.

설계는 최신 구현을 실제로 사용하면서 확인한 문제와 그 근거를 바탕으로 결정한다. 최종 구현 역시 실제 브라우저 렌더링과 상호작용을 통해 평가한다.

## Verification Requirements

### VR-1. 일관된 사용자 작업 흐름과 정보 구조

- 첫 실행부터 프로젝트 등록·선택, Loop 실행, Task 작업, 프로젝트 전환, 관리 작업, 사용 종료 및 재진입까지 하나의 이해 가능한 경험으로 연결되어야 한다.
- 사용자는 현재 어느 프로젝트에서 작업하고 있는지, 해당 Loop의 상태가 무엇인지, 다음에 무엇을 할 수 있는지 쉽게 파악할 수 있어야 한다.
- 프로젝트 관리, 프로젝트 내부 작업, 공통 시스템 관리의 책임과 중요도가 명확하게 구별되어야 한다.
- 일상적으로 사용하는 기능은 불필요한 접기, 스크롤, 화면 전환 또는 내부 개념 탐색 없이 발견하고 접근할 수 있어야 한다.
- 등록 프로젝트가 없는 경우, 하나인 경우, 여러 개인 경우 모두 자연스러운 시작점과 다음 행동을 제공해야 한다.
- 사용자가 프로젝트를 전환하거나 관리 기능에 접근한 뒤 원래 작업을 이어갈 수 있어야 한다.
- 기존 페이지 구성과 내비게이션 방식을 유지할 필요는 없지만, 새로운 구조 역시 불필요한 탐색 단계를 만들지 않아야 한다.

### VR-2. 명확한 프로젝트 등록·선택·관리

- 기존 로컬 Git 저장소를 UI와 CLI에서 등록할 수 있어야 하며, 두 경로의 등록 결과와 검증 의미가 일치해야 한다.
- Git 저장소 루트, upstream 및 기타 실제 필수 조건을 사용자가 적절한 시점에 이해할 수 있어야 한다.
- 등록 전 대상 프로젝트를 확인할 수 있고, 등록 성공 후 다음 행동으로 자연스럽게 이어져야 한다.
- 유효하지 않은 경로, 누락된 Git 설정, 중복 등록 및 접근 실패는 구체적인 원인과 복구 방법을 제공해야 한다.
- 프로젝트 이름, 경로 및 관리 상태를 구별할 수 있어야 한다. 이름이 동일한 프로젝트도 잘못 선택하거나 조작하지 않아야 한다.
- 등록과 관리 해제가 Git 저장소 및 별도 Loop 데이터에 미치는 영향을 이해할 수 있어야 한다.
- 프로젝트 전환·등록·관리 해제가 다른 프로젝트의 Task, 초안, Workflow, 실행 상태를 혼합하거나 손상시키지 않아야 한다.

### VR-3. 프로젝트 작업에 집중할 수 있는 Operator 경험

- 프로젝트의 중심 작업은 Task 목록·상세 조회, Accepted Plan 발행, State와 Blocked By 관리, 댓글, Workpad 및 Human Review여야 한다.
- 사용자는 Task를 선택하고 진행 상황을 확인하거나 새 Plan을 발행하는 주요 행동을 자연스럽게 발견할 수 있어야 한다.
- 실행 상태와 필요한 Loop 제어는 해당 프로젝트의 작업 맥락에서 이해 가능해야 한다.
- 빈 목록, 진행 중 작업, 완료된 작업, 실패 또는 Human Review가 필요한 작업의 구분과 다음 행동이 명확해야 한다.
- 프로젝트 관리 및 Runtime·Workflow 관리 기능이 일상적인 Task 작업의 주의를 불필요하게 빼앗지 않아야 한다.
- 프로젝트 전환과 화면 이동 중 입력 중인 초안이나 작업 맥락을 부당하게 잃지 않아야 한다.
- 기존 Task 데이터와 작업 상태의 의미는 변경하지 않아야 한다.

### VR-4. 이해 가능한 CLI와 종료·재진입 경험

- CLI는 프로젝트를 중심으로 한 사용자의 사고방식에 맞춰 주요 작업을 수행할 수 있어야 한다.
- 프로젝트 등록, 목록 확인, Loop 시작·중지, Manager 열기·종료, 업데이트 및 복구 경로가 발견 가능하고 일관되어야 한다.
- 일반적인 명령 실행에 내부 UUID나 프로세스 구조를 불필요하게 암기할 필요가 없어야 한다.
- UI와 CLI에서 같은 작업을 수행할 때 대상, 결과, 실패 이유가 일치해야 한다.
- 브라우저 화면 닫기, Manager Service 종료, 개별 Loop 정지, 모든 Loop의 정지와 사용 종료가 서로 다른 행동으로 명확하게 구분되어야 한다.
- 사용자는 Manager Service를 명시적으로 종료할 수 있어야 하며, 이 조작이 실행 중인 Loop나 Worker를 암묵적으로 종료해서는 안 된다.
- 모든 작업을 종료하고자 할 때도 영향을 받는 대상을 이해하고 안전하게 수행할 수 있어야 한다.
- Manager 종료·재시작 이후에도 기존 실행 중 Loop를 안전하게 다시 발견하고 관리할 수 있어야 한다.

### VR-5. 명확한 시스템 관리와 오류 복구

- 공통 Runtime 관리와 프로젝트별 Workflow 관리를 혼동하지 않아야 한다.
- 업데이트가 영향을 미치는 대상과 영향을 미치지 않는 대상, 재시작 필요 여부, 실행 중 Loop의 버전 보호 상태를 이해할 수 있어야 한다.
- Source Checkout, Active Runtime, Manager Service 및 실행 중 Loop의 Runtime 관계가 사용자에게 필요한 수준으로 설명되어야 한다.
- 일반적인 작업 상태와 사용자의 개입이 필요한 이상 상태를 구별해야 한다.
- Failed, Unconfirmed, Runtime 손상, 업데이트 실패, 인증 실패 및 Manager 연결 실패가 모두 동일한 일반 오류로 표현되어서는 안 된다.
- 오류와 복구 안내는 해당 작업 맥락에 배치되어야 하며, 진단 정보는 필요할 때 접근 가능해야 한다.
- Manager가 정상 동작하지 않을 때도 해당 Manager UI에 의존하지 않는 진단·복구 경로가 유지되어야 한다.

### VR-6. 안전하고 자연스러운 로컬 브라우저 접근

- 로컬 Manager의 인증, 요청 출처 및 Host 검증은 외부 웹사이트의 무단 관리 요청을 방어해야 한다.
- 정상적인 `127.0.0.1` 및 `localhost` 접근이 불필요한 Host 오류를 만들지 않아야 한다.
- CLI에서 Manager를 열거나 브라우저에서 재진입하는 일반적인 경험이 명확하고 신뢰할 수 있어야 한다.
- 인증 정보가 없거나 유효하지 않은 경우 사용자는 그 이유와 안전한 재인증 방법을 이해할 수 있어야 한다.
- Manager 재시작, Runtime 업데이트 및 복구 이후 인증 상태의 변화가 기존 브라우저 탭을 설명 없는 실패 상태로 남겨두지 않아야 한다.
- 인증 갱신 및 재진입이 민감한 토큰의 불필요한 노출이나 무단 권한 부여를 허용해서는 안 된다.
- 개선된 접근 방식도 임의 원격 요청, DNS rebinding, Cross-Origin 요청 및 권한 없는 관리 작업에 대한 보호를 유지해야 한다.

### VR-7. 일관된 시각적 언어와 정보 위계

- UI는 무채색과 하나의 경고색만으로 구성되어야 한다.
- 선택, 정상 실행, 성공, 진행 중, 비활성화 등은 서로 다른 유채색에 의존하지 않고 이해 가능해야 한다.
- 경고색은 실제 주의 또는 사용자 개입이 필요한 상황에만 사용하며, 정보의 의미를 색상에만 의존해 전달해서는 안 된다.
- 타이포그래피, 공간, 정렬, 그룹화 및 필요한 경계가 정보와 행동의 위계를 형성해야 한다.
- 접기는 드물게 사용하거나 위험한 기능, 선택적 세부 정보 또는 상세 진단 정보를 다루는 보조 수단이어야 한다. 핵심 내비게이션이나 자주 사용하는 주요 작업을 숨기는 기본 구조로 사용해서는 안 된다.
- 넓은 화면과 좁은 화면, 키보드 사용 환경에서 동일한 작업 의미와 우선순위가 유지되어야 한다.
- 실제 사용 색상, 토큰, 의미, 사용 금지 사례, 접기 사용 원칙 및 디자인 철학이 `docs/DESIGN.md`에 명시되어야 한다.
- 시각적으로 정돈된 인상뿐 아니라 실제 정보 발견, 작업 집중 및 상호작용 경험이 개선되어야 한다.

### VR-8. 기존 실행·데이터·보안 계약 보존

- Manager Service, Manager UI 및 각 Loop Process의 독립적인 생명주기를 유지해야 한다.
- Manager 종료나 재시작이 기존 Loop의 Worker 작업을 부당하게 중단해서는 안 된다.
- Loop의 프로세스 신원과 소유권이 확인되지 않은 상태에서 잘못된 프로세스를 제어하지 않아야 한다.
- 인스턴스별 설정, SQLite Task Store, Workflow 및 workspace의 격리를 유지해야 한다.
- 기존 Task 발행과 변경, Accepted Plan 불변성, State, Blocked By, 댓글, Workpad, Human Review 및 Worker 실행 계약을 유지해야 한다.
- Runtime의 불변 배포·안전한 활성화, 실행 중 버전 보호, Workflow 업데이트의 명시적 적용 및 백업 계약을 유지해야 한다.
- Git 저장소와 지속 데이터의 보존, 관리 해제 의미 및 실패 후 복구 안전성을 유지해야 한다.
- 임의 셸 실행 API를 도입하거나 Worker 실행 권한·sandbox·승인 경계를 확장하지 않아야 한다.
- UX 재설계를 위해 기존 정상 동작하는 실행 엔진이나 데이터 시스템을 불필요하게 재구현하지 않아야 한다.

### VR-9. 실제 결과에 대한 독립적인 검토 가능성

- 주요 사용자 흐름의 시작부터 결과까지 실제 UI·CLI 동작을 근거로 평가할 수 있어야 한다.
- 성공, 실패, 대기, 전환, 종료 및 복구 등 의미 있는 상태를 검토할 수 있어야 한다.
- 실제 시각적 결과와 상호작용을 판단할 수 있는 대표적인 증거를 저장소에 보존해야 한다.
- 구현 코드와 테스트 통과만으로 시각적·경험적 요구가 충족되었다고 판단해서는 안 된다.
- 최종 구현의 실제 브라우저 렌더링과 조작 결과를 확인해야 하며, 수동 제작 SVG나 합성 디자인 자료를 그 대체 증거로 사용해서는 안 된다.
- 증거의 코드·Runtime·PR HEAD와 관찰 환경을 식별할 수 있어야 한다.
- 직접 관찰, 테스트로 확인된 동작, 추론 및 시뮬레이션의 차이를 명확하게 기록해야 한다.
- 변경된 결과에 대해 새로운 WORKFLOW의 Verification 및 Reviewability Preparation 계약을 충족해야 한다.

## Definitions

- **Project:** 사용자가 관리하고 작업하는 Git 저장소 중심의 대상. 사용자 인터페이스에서는 내부 Instance ID보다 프로젝트의 정체성을 우선한다.
- **Loop Instance:** 등록된 Project에 연결된 독립 설정, Workflow, Task Store, workspace 및 실행 상태를 가진 시스템 관리 단위.
- **Manager Service:** Loop Instance의 등록, 실행 제어, Runtime 및 관리 API를 담당하는 로컬 서비스 프로세스.
- **Manager UI:** 브라우저에서 프로젝트 및 시스템 관리와 Operator에 접근하는 사용자 인터페이스.
- **Operator:** 선택한 프로젝트의 Accepted Plan 발행과 Task 조회·관리 등 실제 작업을 수행하는 사용자 경험.
- **Loop Process:** 해당 Loop Instance의 Task를 처리하는 독립 실행 프로세스.
- **Runtime:** Manager 및 새로운 Loop 실행에 필요한 공통 실행 코드와 의존성의 버전별 배포 단위.
- **Workflow:** Loop Instance별 Worker 실행 규칙을 담은 독립적인 `WORKFLOW.md`.
- **Manager 종료:** Manager Service를 정지하는 행위. 실행 중 Loop 정지와 구별한다.
- **Loop 정지:** 특정 Loop Process의 실행을 정지하는 행위. Manager 종료 및 인스턴스 관리 해제와 구별한다.
- **관리 해제:** Loop Instance를 Manager의 등록 목록에서 제거하는 행위. Git 저장소 및 기존 지속 데이터 삭제와 구별한다.
- **경고색:** 실제 주의 또는 사용자의 개입을 요구하는 상황을 나타내기 위해 허용된 유일한 유채색 계열.
- **접기(Disclosure):** 현재 작업에 반드시 필요하지 않은 내용을 사용자의 선택에 따라 펼쳐 보는 보조 상호작용.
- **직접 UI 증거:** 실제 구현된 UI가 브라우저에서 렌더링되거나 조작된 결과를 관찰하여 얻은 증거. 수동 재현 이미지와 구별한다.

## Decisions

### 1. 기존 인터페이스는 평가 대상이다

현재 ManagerApp과 OperatorApp의 컴포넌트 구조, 페이지 배치, 접기 구성 및 CLI 명령 체계는 설계 권위가 아니다.

최신 HEAD의 실제 사용자 경험을 먼저 조사하고, 확인된 문제를 기준으로 사용자에게 드러나는 정보 구조와 작업 경계를 정한다.

현재 구현을 실제로 사용하면서 발견한 주요 경험 문제와 그 근거를 남긴다. 최종 설계가 해당 문제를 어떻게 해결하는지 실제 사용자 흐름을 통해 비교·검증한다.

프로젝트 관리와 프로젝트 내부 Task 작업의 구분을 분명하게 만드는 방향은 유지하되, 페이지 수, 내비게이션 위치 또는 특정 레이아웃을 사전에 고정하지 않는다.

중요한 경험 변화는 실제 작업 흐름에서 해결하는 문제가 있어야 한다. 현재 구조의 보존이나 변경 자체를 목적으로 삼지 않는다.

### 2. UI와 CLI는 동일한 사용자 작업의 두 인터페이스다

프로젝트 등록, 식별, 시작·중지, 상태 확인과 복구에서 동일한 의미와 서버 권위를 사용한다.

CLI의 사용자 대상 식별 방식은 프로젝트 이름과 현재 작업 맥락을 우선 고려하되, 동일한 이름이나 불명확한 대상이 있을 때 임의로 선택하지 않는다. UUID는 내부의 안정적인 식별자로 유지할 수 있다.

공통 기능을 서로 다른 규칙으로 구현하거나 UI에 별도의 생명주기 권위를 만들지 않는다.

### 3. 관리 범위를 명확하게 유지한다

공통 Runtime과 Manager Service의 관리는 프로젝트별 Workflow 및 Loop Process 관리와 다른 책임이다.

사용자에게는 해당 조작이 전역 관리인지 특정 프로젝트의 관리인지 명확하게 전달한다.

프로젝트 작업 공간은 Task 작업을 중심으로 구성하고, 관리 기능은 필요한 맥락에서 발견 가능하도록 연결한다. 현재 작업과 무관한 전역 관리 정보가 기본 작업을 방해하지 않게 한다.

### 4. 기존 생명주기와 저장 권위는 보호한다

`docs/SYSTEM.md`의 Manager/Loop 독립 생명주기, OS 프로세스 신원 검증, 인스턴스별 지속 데이터 격리, Runtime 활성화 및 Workflow 교체 계약을 유지한다.

UI·CLI 경험에 필요한 Manager 종료 또는 재진입 기능은 기존 경계를 이용하여 구현한다. 별도 실행 엔진이나 중복 프로세스 관리 체계를 만들지 않는다.

Task Store와 Local Publisher의 권위를 유지하며 Worker·Symphony·Codex 실행 구현 및 승인 정책은 이 작업의 변경 대상이 아니다. 해당 경계를 실제로 변경해야 하는 요구가 발견되면 별도 Plan으로 분리한다.

### 5. 로컬 보안의 목적과 사용자 진입 방식을 분리한다

로컬 서비스에 대한 무단 접근을 막는 보안 목적은 유지한다.

단, 정확한 Host 문자열 제한, Runtime ID에 종속된 API 토큰, `file://` 부트스트랩 및 세션 토큰 보관 방식은 구현 선택으로 취급하고 재평가한다.

`localhost`와 `127.0.0.1`을 안전하게 지원할 수 있도록 허용 Host·Origin·바인딩·인증 모델을 일관되게 결정한다.

`localhost`의 IPv4·IPv6 주소 해석과 실제 서비스 바인딩을 확인한다. IPv6 지원 자체를 필수 조건으로 삼지 않으며, 선택한 주소 지원 범위와 접근 방식이 정상 사용과 보안 요구를 충족하도록 한다.

토큰의 유효 기간이나 Runtime 변경 시 무효화가 실제로 어떤 위험을 줄이는지 확인한다. 불필요한 인증 갱신은 제거할 수 있지만, 인증 없는 로컬 관리 권한을 부여하거나 토큰을 임의의 웹사이트에 노출하는 방식은 허용하지 않는다.

브라우저 접근·재인증·기존 탭 복구는 정상적인 사용자 경험의 일부로 취급한다.

### 6. 접기는 정보 구조를 대체하지 않는다

접기 사용 여부는 구현 편의나 단순한 화면 길이가 아니라 정보의 역할, 중요도, 사용 빈도에 따라 결정한다.

주요 작업과 프로젝트 전환처럼 반복적으로 사용하는 기능은 접기에 의존하지 않는다.

긴 로그, 원본 Diff, 과거 복구 상세, 위험하거나 드물게 사용되는 보조 조작에는 접기를 사용할 수 있다.

접기를 제거한다는 이유만으로 내용을 모두 한 화면에 펼치지 않는다. 필요한 경우 탐색 구조와 작업 경계를 먼저 개선한다.

### 7. 색상은 의미를 제한적으로 표현한다

UI의 기본 색상은 무채색으로 제한한다. 유채색은 하나의 경고색 계열만 허용한다.

경고색은 선택 강조나 장식, 정상 진행 상태의 구분에 사용하지 않는다. 실제 주의가 필요한 조건에서만 사용한다.

색상 값을 무작위로 분산시키지 않고 의미 있는 토큰으로 관리한다.

정확한 무채색 단계, 경고색 값, 표면·텍스트·경계·포커스의 관계는 실제 렌더링과 대비 검토를 통해 결정한다. 최종 사용 값과 사용 규칙을 `docs/DESIGN.md`에 기록한다.

시각적 위계는 색상이 없는 상태에서도 성립해야 한다.

### 8. 변경 범위는 사용자 문제와 책임에 따라 결정한다

변경 파일 수나 기존 컴포넌트의 유지 여부로 범위를 제한하지 않는다.

주요 검토 대상은 다음 책임을 가진 구현이다.

- CLI 진입 및 명령 처리: `bin/leesh-loop.mjs`
- 사용자 인터페이스와 상태·탐색 구조: `operator/ui/`
- Manager API, 등록·실행·종료·인증: `operator/app/`의 관련 모듈
- 시스템 및 디자인 계약: `docs/SYSTEM.md`, `docs/DESIGN.md`
- 사용자 안내와 실제 UI 검증 자료: `README.md`, `docs/ui-evidence/`

책임이 변경되거나 분리되면 파일·모듈·컴포넌트·주요 함수 이름도 실제 책임을 반영해야 한다. 단기 구현 맥락이나 추측성 추상화에 의존한 이름을 만들지 않는다.

KISS, YAGNI, DRY에 따라 새 추상화와 중복 상태를 최소화하고 기존 계약의 재사용을 우선한다.

### 9. 실제 구현의 관찰을 설계와 검증의 기준으로 삼는다

이전의 수동 제작 SVG처럼 실제 화면을 충실하게 표현하지 못하는 자료는 현재 UI의 시각적 사실이나 최종 결과를 입증하지 않는다.

기존 테스트, 실제 API 관찰 및 브라우저 캡처는 각각의 관찰 대상과 구현 버전에 부합하는 범위에서 활용할 수 있다. 단, 과거 버전의 실제 캡처라도 변경된 최종 UI의 모습을 입증하지는 않는다.

현재 구현의 사용성 조사와 최종 구현의 검증을 구별한다. 조사 당시의 화면이 최종 설계의 정답이 되어서도 안 된다.

실제 브라우저 화면과 상호작용에 필요한 검증 수단이 부족하면, 허용된 환경에서 해당 수단을 마련하는 작업을 포함한다.

증거를 얻을 수 없다는 이유로 수동 SVG를 제작하여 실제 결과를 대신하지 않는다. 보안·권한 경계는 우회하지 않으며, 직접 검증이 불가능한 요구는 완료로 판단하지 않는다.

## Planned Units

### Unit 1 — Project discovery and management

**Responsibility:** 프로젝트를 발견·등록·선택·전환·관리 해제하는 경험.

**Outcome:** 사용자가 프로젝트를 중심으로 작업 대상을 이해하고, 올바른 Loop Instance를 안전하게 선택하고 관리할 수 있다.

### Unit 2 — Project work experience

**Responsibility:** Operator의 Task 중심 정보 구조, 탐색 및 작업 연속성.

**Outcome:** 사용자가 프로젝트 내부에서 핵심 Task 작업에 집중하고, 상태와 다음 행동을 이해하며, 관리 화면과의 이동에서 작업 맥락을 유지할 수 있다.

### Unit 3 — CLI and lifecycle experience

**Responsibility:** CLI 명령의 사용 모델과 Manager·Loop의 실행, 종료 및 재진입.

**Outcome:** UI와 CLI가 같은 관리 의미를 제공하고, 사용자가 Manager와 Loop를 혼동하지 않고 안전하게 실행·종료할 수 있다.

### Unit 4 — Runtime, Workflow and recovery management

**Responsibility:** 전역 및 프로젝트별 관리 작업의 구분과 업데이트·진단·복구 경험.

**Outcome:** 사용자가 관리 조작의 영향 범위를 이해하고 정상·오류·복구 필요 상태에 적절히 대응할 수 있다.

### Unit 5 — Local browser access and authorization

**Responsibility:** 로컬 주소 접근, 브라우저 부트스트랩, 인증 유지·갱신 및 실패 처리.

**Outcome:** 로컬 보안 경계를 유지하면서 정상적인 Manager 접근, 재시작 이후 재진입 및 인증 복구가 자연스럽게 동작한다.

### Unit 6 — Visual system and design documentation

**Responsibility:** 시각적 언어, 정보 위계, 접기 원칙, 반응형·접근성 규칙 및 디자인 문서.

**Outcome:** 무채색과 단일 경고색의 일관된 UI가 구현되고, 다른 작업에서도 재사용할 수 있는 명확한 디자인 계약이 남는다.

### Unit 7 — Experience verification and reviewability

**Responsibility:** 실제 사용자 흐름과 최종 렌더링·상호작용을 검증하고 독립적으로 판단 가능한 증거를 보존하는 능력.

**Outcome:** UI와 CLI의 최종 결과를 코드 설명이나 합성 자료에 의존하지 않고 재검토할 수 있다.

## Verification

### V-1. 전체 사용자 여정과 정보 구조 (VR-1)

격리된 사용자 환경에서 실제 CLI와 Manager를 실행한다. 등록 프로젝트가 없는 초기 상태, 하나의 프로젝트, 여러 프로젝트 상태를 관찰한다.

현재 구현의 사용자 흐름을 먼저 실제로 경험하고, 주요 사용성 문제 및 발생 조건을 기록한다.

첫 실행 → 등록 → 선택 → Loop 실행 → Task 작업 → 프로젝트 전환 → 관리 → 종료 → 재진입의 연결된 흐름을 최종 구현에서도 실제 조작한다.

각 단계에서 현재 프로젝트, 상태, 주요 행동 및 다음 이동 경로를 판단할 수 있는지 확인하고, 기존에 확인한 문제가 어떻게 해결되었는지 비교한다.

**Pass:** 주요 행동을 자연스럽게 발견하고 실행하며, 프로젝트 맥락과 작업 위치를 잃지 않는다. 별도의 내부 구조 설명이나 불필요한 접기 탐색이 필요하지 않다. 기존에 확인된 주요 사용성 문제가 해결되었음을 실제 사용 흐름에서 확인할 수 있다.

**Failure:** 현재 위치나 조작 대상이 불명확하거나, 주요 작업을 발견하기 위해 숨겨진 관리 영역을 반복 탐색해야 한다. 기존 문제의 해결을 실제 결과로 확인할 수 없다.

### V-2. 프로젝트 등록과 전환 (VR-2)

서로 다른 이름과 동일한 이름을 가진 테스트 Git 저장소, 정상·누락·잘못된 upstream, 중복 등록 및 무효 경로를 포함한 대표 사례를 확인한다.

UI 등록과 CLI 등록에 대해 Manager API·registry·파일 시스템을 직접 조회한다.

프로젝트 전환과 관리 해제 전후에 다른 인스턴스의 상태와 지속 데이터를 비교한다.

**Pass:** 올바른 대상을 등록·선택·관리하고, 오류가 이해 가능하며, 대상 외 프로젝트와 지속 데이터에 영향이 없다.

**Failure:** 잘못된 프로젝트를 선택·조작하거나, 등록 조건을 이해할 수 없거나, 데이터가 혼합·삭제된다.

### V-3. Task 작업 연속성과 기존 Operator 계약 (VR-3, VR-8)

실제 Manager와 서로 다른 Local Task Store를 사용하여 Plan 발행, Task 상세, State, Blocked By, 댓글, Workpad 및 Human Review의 대표 흐름을 검증한다.

프로젝트 전환과 재진입 중 초안 및 표시 데이터가 올바른 인스턴스에 속하는지 확인한다.

필요한 경우 SQLite 직접 조회로 API 표시 결과와 권위 있는 저장 상태를 비교한다.

**Pass:** 주요 Task 작업이 자연스럽고 기존 데이터·상태 의미가 보존된다.

**Failure:** 인스턴스 혼합, 초안 손실, Task 의미 변경, 저장 결과와 화면의 불일치가 발생한다.

### V-4. CLI와 Manager·Loop 생명주기 (VR-4, VR-8)

실제 CLI 진입점으로 실행·목록·시작·중지·종료·재진입을 수행한다.

Manager Service와 Loop Process의 PID·시작 신원, 포트 및 실행 상태를 관찰한다.

실행 중인 Loop를 유지한 채 브라우저와 Manager Service를 각각 종료·재시작하고, Loop 작업 및 상태가 유지되는지 확인한다.

전체 사용 종료 경로에서는 조작 대상과 최종 종료 상태를 확인한다.

**Pass:** 종료 대상이 정확하며, Manager 종료 후 Loop가 계속 동작하고 재진입 시 안전하게 복원된다.

**Failure:** 무관한 Loop 중단, 프로세스 신원 오판, 설명과 다른 종료 결과 또는 Manager 재진입 실패가 발생한다.

### V-5. Runtime·Workflow 및 복구 (VR-5, VR-8)

Runtime 설치·업데이트, 최신 상태의 반복 업데이트, Manager 재시작 필요, 인스턴스별 Workflow 비교·적용 및 대표 실패 상태를 확인한다.

적용 전후 Runtime ID, Manager 실행 버전, Loop 버전, Workflow 백업과 지속 데이터 상태를 직접 비교한다.

Manager가 정상 동작하지 않는 조건에서 CLI를 통한 독립 복구 경로도 확인한다.

**Pass:** 변경 영향이 명확하고 실제 결과와 일치하며, 실행 중 Loop와 기존 데이터가 보호된다.

**Failure:** 잘못된 영향 범위를 안내하거나, 부분 적용을 성공으로 표현하거나, 독립 복구 경로가 작동하지 않는다.

### V-6. 로컬 주소 및 인증 보안 (VR-6)

실제 브라우저와 HTTP 요청을 통해 `127.0.0.1`, `localhost`, 정상 인증, 인증 정보 부재, 이전 토큰, Manager 재시작 및 Runtime 변경 후 재진입을 확인한다.

Host·Origin·Fetch Metadata 변조, 잘못된 토큰, 교차 출처 및 DNS rebinding에 해당하는 요청을 통해 무단 API 접근이 거부되는지 검증한다.

`localhost`의 이름 해석, 실제 서비스 바인딩 및 브라우저 출처 차이에 따른 접근 결과를 확인한다. IPv6 지원 자체를 필수 판정 조건으로 삼지 않으며, 선택한 주소 지원 범위에서 정상 접근과 보안 검증이 일관되는지 평가한다.

**Pass:** 정상 로컬 사용자는 안전하게 접근하고 재인증할 수 있으며, 무단 요청은 거부된다. 인증 상태 변화가 설명 없는 실패로 남지 않는다.

**Failure:** 정상적인 접근이 불필요하게 차단되거나, 다른 출처가 권한 없이 관리 작업을 수행하거나, 세션 복구가 불가능하다.

### V-7. 디자인과 반응형 사용성 (VR-7)

최종 코드에서 빌드한 실제 UI를 브라우저에서 실행하고 데스크톱 및 좁은 화면의 주요 상태를 관찰한다.

프로젝트 목록, 작업 공간, Task 상세, Plan 발행, 관리 화면과 오류·경고·복구 상태의 실제 렌더링을 확인한다.

키보드 이동, 포커스, 시각적 위계, 가독성, 경고의 의미, 접기 사용 및 색상 대비를 평가한다.

실제 CSS 색상 사용을 조사하여 문서화된 무채색·단일 경고색 규칙과 비교한다.

**Pass:** 핵심 정보와 행동이 쉽게 발견되며, 색상과 접기 원칙이 일관되고, 화면 크기 및 입력 방식에 따라 의미가 손실되지 않는다.

**Failure:** 시각적 정돈에도 불구하고 주요 작업이 숨겨지거나, 불필요한 유채색·경계·접기에 의존하거나, 문서와 구현이 불일치한다.

### V-8. 실행·데이터 보호 회귀 (VR-8)

격리된 XDG 환경과 복수의 Git 저장소를 사용하여 Manager API, Registry, Runtime, Loop 생명주기, Task Store 및 Workflow 관련 회귀 테스트를 실행한다.

실제 프로세스·파일 시스템·SQLite 결과가 중요한 경계에서는 통합 검증을 사용한다.

기존 Worker 실행 계약에 영향을 미치는 변경이 없다면 해당 엔진의 재구현이나 불필요한 광범위 검증은 수행하지 않는다. 변경이 실제로 경계를 건드린 경우에는 그 범위의 추가 검증을 수행한다.

**Pass:** 관련 기존 계약과 변경된 경계가 유지되고, 데이터 손상이나 실행 격리 회귀가 없다.

**Failure:** 기존 정상 동작을 깨뜨리거나 변경 범위 밖의 실행 의미를 변형한다.

### V-9. 증거 보존과 Reviewability Preparation (VR-9)

최종 구현의 실제 브라우저 캡처, 대표 상호작용 기록, CLI 출력, Manager API 결과 및 필요한 프로세스·SQLite 검증 결과를 저장소에 보존한다.

시각적 증거는 실제 브라우저에서 캡처한 이미지로 남기고, 캡처 당시의 코드 HEAD, Runtime 식별자, 환경 및 상태를 명시한다. 상호작용 결과는 스크린샷만으로 확인할 수 없는 경우 적절한 조작 기록과 권위 있는 결과를 함께 보존한다.

증거는 `docs/ui-evidence/`에 정리하고, 실제 구현에 대응하는 새로운 기록과 기존 역사적·합성 자료를 명확히 구별한다. 민감한 토큰 및 실제 사용자 데이터는 포함하지 않는다.

기존 사용성 조사에서 확인한 주요 문제와 최종 구현에서의 해결 여부를 연결하여 기록한다.

최종 PR/HEAD에 대해 새로운 WORKFLOW의 독립 Reviewability Preparation을 수행한다.

**Pass:** 독립 검토자가 최종 디자인과 주요 동작 결과를 실제 증거로 판단할 수 있으며, Reviewability Preparation을 통과한다.

**Failure:** 최종 화면이 검증되지 않았거나, 증거가 다른 구현을 가리키거나, 합성 자료에 의존하여 실제 UI 결과를 주장하거나, 중요한 결과의 검토 수단이 합리적으로 마련될 수 있음에도 누락되어 있다.

### Verification limitations

특정 외부 서비스, 빌드 의존성 또는 브라우저 제약으로 실제 검증이 불가능한 경우에는 검증 대상과 차단 원인을 구체적으로 기록한다.

먼저 허용된 범위에서 검증 환경이나 관찰 수단을 마련한다. 직접 결과를 재현할 수 없는 경우 가장 가까운 유효한 증거와 남은 불확실성을 구별한다.

검증되지 않은 요구를 테스트 설명이나 합성 자료만으로 완료 처리하지 않는다. 필수 검증의 부족이 해소되지 않으면 WORKFLOW의 Human Review 절차에 따라 처리한다.
