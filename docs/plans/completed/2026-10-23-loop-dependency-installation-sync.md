# 2026-10-23-loop-dependency-installation-sync

## Objective

생성된 각 Leesh Loop가 `leesh-loop init`, `leesh-loop update` 및 이후 실행 과정에서 현재 의존성 정의에 일치하는 npm 의존성을 설치하고 사용하도록 보장한다.

기존 런타임 업데이트와 의존성 준비의 책임 분리는 유지한다.

## Intent

Leesh Loop는 Operator UI와 Local Task Store의 npm 의존성을 각각 선언하고, 예상 설치 파일이 없으면 해당 의존성을 설치한다.

그러나 현재 설치 여부 검사는 주로 실행 파일이나 네이티브 바이너리의 존재에 의존한다. 따라서 `leesh-loop update`로 의존성 정의가 변경되어도 기존 설치 파일이 남아 있다면 재설치를 생략할 수 있다.

그 결과 새로운 lockfile이 적용되었음에도 이전 버전의 의존성을 사용하여 Loop가 실행될 수 있다.

이번 작업은 단순한 파일 존재 여부 대신 **현재 의존성 정의와 성공적으로 준비된 설치 상태의 일치 여부**를 기준으로 의존성 재사용을 결정하도록 개선한다.

원본 저장소의 의존성 버전 선택, 취약점 자동 탐지 및 자동 업데이트는 별도 문제로 다룬다.

## Verification Requirements

### VR1. 의존성 일치성

- 지원되는 런타임 실행 경로에서 각 구성 요소는 현재 의존성 정의를 기준으로 성공적으로 준비된 npm 의존성을 사용해야 한다.
- 실행 파일이나 네이티브 바이너리가 존재한다는 이유만으로 기존 설치를 최신 상태로 판단해서는 안 된다.
- 의존성 버전 변경, 추가 및 제거 사항은 해당 구성 요소가 의존성을 사용하기 전에 실제 설치 상태에 반영되어야 한다.
- 변경되지 않은 유효한 설치는 불필요한 재설치 없이 재사용해야 한다.
- 실행마다 `node_modules` 전체의 무결성을 검사하는 것은 요구하지 않는다. 다만 감지 가능한 필수 설치 파일 누락이나 알려진 무효화 상태를 무시해서는 안 된다.

### VR2. 초기화 및 런타임 업데이트

- 새로 초기화된 Loop는 지원되는 실행 경로에서 필요한 npm 의존성을 자동으로 준비해야 한다.
- `leesh-loop update`는 기존처럼 관리 대상 의존성 정의를 생성된 Loop에 전파해야 한다.
- 업데이트로 의존성이 변경되면 다음 실행에서 해당 의존성을 사용하기 전에 새로운 설치 상태를 준비해야 한다.
- 사용자가 `node_modules`를 삭제하거나 `npm install`, `npm ci`를 수동 실행할 필요가 없어야 한다.
- 의존성이 변경되지 않은 업데이트는 유효한 기존 설치의 재설치를 강제하지 않아야 한다.
- 기존 설치 기록이 없는 Loop도 재초기화 없이 새로운 관리 방식으로 전환할 수 있어야 한다.

### VR3. 실패 및 복구

- 의존성 설치 또는 일치성 확인에 실패한 구성 요소는 검증되지 않은 설치 상태로 실행되어서는 안 된다.
- 실패한 구성 요소와 준비 실패 원인을 식별할 수 있어야 한다.
- 실패하거나 중단된 준비가 성공적인 설치로 기록되어서는 안 된다.
- 이전에 성공한 설치 기록이 있더라도 이후 준비 실패로 설치 상태가 불확실해지면 이를 최신 설치의 증거로 재사용해서는 안 된다.
- 일시적 실패 이후 재시도를 통해 수동 메타데이터 정리 없이 복구할 수 있어야 한다.
- 기존 실행 구조에서 발생할 수 있는 준비 작업 간 충돌이 잘못된 설치 승인으로 이어져서는 안 된다.

### VR4. 기존 동작과 범위 보존

- 생성된 Loop의 독립적인 구조와 기존 시작 및 업데이트 명령을 유지한다.
- `leesh-loop update`는 런타임 파일 동기화를 담당하고, 실제 의존성 준비는 해당 런타임이 다음에 필요해질 때 수행한다.
- `leesh-loop update --workflow`는 별도의 워크플로 업데이트 작업으로 유지한다.
- 인스턴스별 설정, 워크플로 파일, Task 데이터 및 Worker 워크스페이스를 보존한다.
- 기존에 지원되는 런타임 실행 경로를 대상으로 하며, 임의의 내부 모듈 직접 실행까지 새로운 지원 계약을 확장하지 않는다.
- 구성 요소별 의존성 정의를 루트 패키지로 통합하도록 강제하지 않는다.
- 원본 저장소의 의존성 자동 업그레이드, GitHub 보안 자동화 및 등록된 모든 Loop 인스턴스에 대한 자동 업데이트는 도입하지 않는다.

## Definitions

- **원본 배포본(Source distribution):** 생성된 Loop에 런타임 파일을 제공하는 설치된 Leesh Loop 소스.
- **생성된 Loop(Generated Loop):** `leesh-loop init`으로 생성한 독립적인 Loop 인스턴스.
- **런타임 구성 요소(Runtime component):** npm 의존성을 독립적으로 관리하는 구성 요소. 현재 Operator UI와 Local Task Store.
- **의존성 정의(Dependency definition):** 해당 구성 요소의 `package.json`과 `package-lock.json`.
- **설치된 의존성(Installed dependencies):** 해당 구성 요소의 설치 디렉터리에 실제로 존재하는 npm 패키지.
- **의존성 준비(Dependency preparation):** 현재 의존성 정의에 맞는 설치 상태를 확립하고 그 성공 여부를 확인하는 작업.
- **설치 기록(Installation record):** 특정 의존성 정의에 대한 준비 성공을 나타내는 로컬 기록.
- **유효한 설치(Valid installation):** 현재 의존성 정의에 대한 성공적인 준비가 확인되었고, 감지 가능한 필수 파일 누락이나 알려진 무효화 상태가 없는 설치.
- **지원 실행 경로(Supported execution path):** 기존 Leesh Loop가 공식적으로 제공하는 런타임 실행 및 해당 구성 요소 사용 경로. 내부 모듈의 임의 직접 실행은 포함하지 않는다.
- **런타임 업데이트(Runtime update):** `leesh-loop update`가 수행하는 관리 대상 파일 동기화 작업. 의존성 준비와 구분한다.

## Decisions

### D1. 구성 요소별 npm 의존성 관리 유지

기존 패키지 경계를 유지한다.

| 구성 요소 | 의존성 정의 |
|---|---|
| Operator UI | `operator/ui/package.json`, `package-lock.json` |
| Local Task Store | `operator/local_task_store/package.json`, `package-lock.json` |
| 생성된 Loop 루트 | 생성된 루트 패키지와 lockfile |

루트 패키지는 Loop 수준의 명령을 담당하며 각 구성 요소의 의존성을 중복 선언하지 않는다.

Elixir Mix 의존성과 외부 호스트 도구는 기존 관리 방식에 맡긴다.

### D2. 성공적인 의존성 준비를 기준으로 재사용 판단

기존 설치의 재사용 여부는 현재 의존성 정의와 성공적인 준비 상태를 기준으로 판단한다.

재사용하려면 다음 조건이 충족되어야 한다.

- 현재 의존성 정의가 마지막으로 성공적으로 준비된 정의와 일치한다.
- 필요한 설치 파일이 존재한다.
- 설치가 불완전하거나 무효화되었다는 사실이 없다.

이 계약은 실제 `node_modules` 전체의 무결성을 매번 증명하는 것이 아니라, **현재 정의에 대한 성공적인 설치 이력과 감지 가능한 설치 상태를 확인하는 것**이다.

설치 기록의 구체적인 저장 형식과 비교 방식은 구현에서 결정한다.

### D3. lockfile 기반 설치 유지

npm 의존성 준비에는 `npm ci`를 사용한다.

생성된 Loop의 실행 과정에서 `npm install`로 의존성 정의를 암묵적으로 변경하지 않는다.

`package.json`과 lockfile이 일치하지 않으면 자동 수정하지 않고 준비를 실패 처리한다.

버전 변경, 추가, 제거는 동일한 준비 계약으로 처리한다.

### D4. 실행 시 준비 및 지원 경로 유지

`leesh-loop update`는 관리 대상 런타임 파일을 교체하는 역할을 유지한다. 업데이트 명령이 직접 의존성을 설치할 필요는 없다.

의존성이 필요한 지원 실행 경로에서는 해당 구성 요소가 의존성에 접근하기 전에 준비를 완료한다.

기존 시작 절차에서 필요한 의존성을 선행 준비하는 방식은 유지할 수 있다.

새로운 계약을 충족한다는 이유로 임의의 내부 모듈이나 개발 전용 실행 경로까지 지원 대상으로 확대하지 않는다.

### D5. 구성 요소별 설치 상태 독립 관리

각 런타임 구성 요소는 자신의 의존성 준비 상태를 독립적으로 관리한다.

한 구성 요소의 의존성 변경은 다른 구성 요소의 유효한 설치를 무효화하지 않는다.

설치 상태는 생성된 Loop 내부의 로컬 상태로 유지하며 원본 배포본의 관리 대상 런타임 파일과 구분한다.

설치 기록이 없는 기존 Loop의 상태는 신뢰할 수 있는 성공 기록으로 간주하지 않는다. 필요한 경우 최초 1회 재준비하여 새로운 기준을 확립할 수 있다.

이러한 전환은 Loop 재초기화나 사용자 데이터 삭제를 요구해서는 안 된다.

### D6. 준비 실패와 복구 경계

설치 성공 기록은 준비가 성공적으로 완료된 후에만 유효해야 한다.

준비를 시작하거나 진행하는 과정에서 기존 설치가 변경되어 유효성이 불확실해지면, 이전 성공 기록을 근거로 이를 재사용해서는 안 된다.

준비 실패 후 재시도는 지원되어야 하며, 사용자가 설치 기록을 직접 제거할 필요가 없어야 한다.

동시 준비에 대해서는 기존 지원 실행 구조에서 실제로 발생 가능한 충돌을 안전하게 처리한다. 별도의 범용 패키지 설치 조율 시스템을 만드는 것은 이번 작업의 목적이 아니다.

### D7. 기존 모듈 책임 유지

다음 영역의 기존 책임을 유지한다.

- `operator/app/update.mjs`: 관리 대상 런타임 파일 업데이트 및 배포 설치 메타데이터
- `operator/app/prepare-runtime.mjs`: 기존 런타임 준비 조율
- `operator/app/leesh-loop.mjs`: Loop 시작 및 Operator UI 조율
- `operator/app/local-task-store-runtime.mjs`: Local Task Store 로딩과 의존성 준비
- `operator/app/runtime-manifest.mjs`: 런타임 스냅샷 파일 선택
- `operator/app/init.mjs`: 독립적인 Loop 생성

중복되는 의존성 준비 판단은 필요에 따라 책임이 명확한 공통 모듈로 분리할 수 있다.

파일, 모듈, 타입 및 주요 함수 이름은 일시적인 구현 상황이 아니라 장기적으로 유지될 실제 책임을 표현해야 한다.

새로운 런타임 파일이 필요한 경우 기존 스냅샷 체계를 통해 생성된 Loop와 런타임 업데이트에 포함되어야 한다.

### D8. 보호할 기존 영역

다음 영역의 의미와 생명주기는 변경하지 않는다.

- `project.toml` 및 인스턴스별 설정
- `WORKFLOW.md` 및 명시적인 워크플로 업데이트
- Local Task Store의 영속 데이터
- Worker 워크스페이스
- Symphony Mix 의존성 관리
- 전역 Loop 인스턴스 등록
- 원본 저장소의 의존성 버전 선택
- GitHub 보안 자동화

새로운 의존성 준비 기능을 위해 기존 배포 설치 메타데이터를 다른 용도로 재정의하지 않는다.

보호 영역을 변경해야 하는 상황이 발생하면 기존 검증 요구사항을 충족하는 데 필요한 최소 범위로 제한한다. 그 밖의 변경은 별도로 다룬다.

## Planned Units

### Unit 1. 의존성 일치성 및 준비

**책임:** 독립적인 npm 런타임 구성 요소에 대해 의존성 정의와 설치 상태의 일치성을 판단하고 준비하는 기능을 제공한다.

**예상 결과:**

- 현재 의존성 정의에 따라 기존 설치의 재사용 여부를 결정한다.
- 누락되었거나 오래되었거나 유효하지 않은 설치를 lockfile에 맞게 준비한다.
- 성공적인 준비만 유효한 설치 상태로 인정한다.
- 실패하거나 불완전한 준비 상태에서 안전하게 재시도할 수 있다.
- 구성 요소별 설치 상태가 독립적으로 유지된다.

**관련 요구사항:** VR1, VR3.

### Unit 2. 생성된 Loop 생명주기 통합

**책임:** 생성된 Loop의 기존 초기화, 업데이트 및 지원 실행 경로에서 필요한 의존성 준비가 수행되도록 한다.

**예상 결과:**

- 새로운 Loop는 실행 시 필요한 의존성을 준비한다.
- 기존 Loop는 업데이트로 전달된 의존성 변경을 인식한다.
- 영향을 받은 런타임 구성 요소가 실행되기 전에 필요한 설치를 완료한다.
- 변경되지 않은 유효한 설치는 재사용한다.
- 기존 Loop는 재초기화 없이 새로운 설치 관리 방식으로 전환된다.
- 워크플로 전용 업데이트 및 인스턴스의 영속 상태는 영향을 받지 않는다.

**관련 요구사항:** VR2, VR4.

## Verification

### V1. 의존성 변경 동기화

**대상:** VR1, VR2.

이전 lockfile을 기준으로 의존성이 이미 설치된 격리 Loop에서 의존성 정의를 변경하고, 런타임 업데이트 이후 실제 실행을 검증한다.

검증 상황:

- 기존 패키지 버전 변경
- 새 패키지 추가
- 기존 패키지 제거
- 기존 설치 파일이 남아 있는 상태에서 업데이트
- 의존성 변경 없는 업데이트 및 반복 실행

실제 설치된 패키지 버전과 사용 여부를 확인한다. 선언 파일의 변경만으로 설치 성공을 판단하지 않는다.

**통과:** 실제 설치와 실행에 사용되는 의존성이 현재 정의에 일치하며, 변경되지 않은 유효한 설치는 재사용된다.

**실패:** 오래된 의존성이 계속 사용되거나 유효한 설치를 불필요하게 재설치한다.

### V2. 초기화 및 실행 경로 통합

**대상:** VR2, VR4.

격리된 생성 Loop에서 실제 지원 명령 경로를 사용하여 다음 상황을 확인한다.

- `leesh-loop init` 이후 최초 실행
- 최초 실행 이전의 런타임 업데이트
- 기존 설치 이후의 런타임 업데이트
- 업데이트 이후 `npm start`
- Local Task Store를 사용하는 기존 지원 실행 경로
- 의존성 변경 없는 반복 실행
- `leesh-loop update --workflow`

필요한 의존성이 실제 사용 전에 준비되었는지 확인한다.

**통과:** 지원 경로에서 수동 의존성 설치 없이 정상적인 준비가 이루어지고 기존 명령의 책임이 유지된다.

**실패:** 지원 경로가 필요한 준비를 우회하거나 업데이트 경계를 변경한다.

### V3. 실패, 전환 및 재시도

**대상:** VR2, VR3.

다음 상태를 검증한다.

- `package.json`과 lockfile 불일치
- npm 설치 실패 및 중단
- 성공 기록은 있지만 필요한 설치 파일이 누락된 상태
- 설치 기록이 없는 기존 Loop
- 준비 실패 이후 재시도
- 기존 실행 구조에서 발생 가능한 준비 작업 충돌

종료 상태, 오류 메시지, 실제 설치 상태 및 이후 복구 동작을 관찰한다.

**통과:** 불완전한 설치를 실행에 사용하지 않고, 실패 원인을 확인할 수 있으며, 수동 메타데이터 정리 없이 재시도하거나 기존 Loop를 전환할 수 있다.

**실패:** 실패한 준비가 성공으로 인정되거나, 이전 기록으로 잘못된 설치를 재사용하거나, 재초기화 및 수동 복구가 필요하다.

### V4. 구성 요소 독립성

**대상:** VR1, VR4.

UI 또는 Local Task Store 중 하나의 의존성 정의만 변경한 뒤 양쪽의 준비 동작을 확인한다.

**통과:** 영향을 받은 구성 요소만 필요한 동기화를 수행하며, 다른 구성 요소의 유효한 설치는 재사용된다.

**실패:** 무관한 구성 요소의 설치가 불필요하게 무효화되거나 필요한 동기화가 생략된다.

### V5. 인스턴스 상태 보존

**대상:** VR4.

대표적인 설정, 워크플로 내용, Task 데이터 및 워크스페이스 파일을 가진 격리 Loop에 의존성 변경을 포함한 런타임 업데이트를 적용한다.

업데이트 및 의존성 준비 이후 해당 상태를 비교한다.

**통과:** 의존성 동기화가 성공하고 보호 대상 인스턴스 상태가 유지된다.

**실패:** 보호 대상 설정이나 영속 데이터가 변경되거나 워크플로 업데이트 동작이 달라진다.

### V6. 격리 환경에서의 검증

검증은 작업 저장소와 `/tmp`에만 접근할 수 있는 환경에서도 가능한 범위에서 수행한다.

- 테스트용 저장소, 생성된 Loop, 설치 기록, 임시 캐시 및 테스트 데이터를 접근 가능한 경로에 격리한다.
- 사용자의 실제 Loop 인스턴스, 전역 레지스트리 및 호스트 영속 설정에 대한 접근을 필수 전제로 삼지 않는다.
- 테스트 과정에서 접근 제한 영역에 파일을 생성하거나 기존 상태를 변경하지 않는다.
- npm 레지스트리 접근이나 필요한 패키지 캐시가 없는 경우 실제 설치 검증의 한계를 명시한다.
- 가능한 경우 실제 명령 진입점과 실제 설치 결과를 검증한다.
- 외부 연동의 제약으로 전체 경로를 실행할 수 없다면 검증 가능한 부분과 검증하지 못한 부분을 구분한다.
- 모의 검증이나 부분 통합 검증을 전체 실행 성공의 증거로 취급하지 않는다.

격리 환경의 제약을 해결하기 위해 제품 런타임에 불필요한 새 설정이나 범용 테스트 인프라를 도입하지 않는다.

**통과:** 검증 실행이 허용된 파일시스템 경계를 지키며 수행되고, 실제로 확보한 증거와 검증하지 못한 요구사항이 구분된다.

**실패:** 테스트가 접근 제한 영역에 의존하거나, 검증하지 못한 외부 동작을 성공했다고 판단한다.

## Verification Tools

| 도구 또는 메커니즘 | 확인할 증거 |
|---|---|
| Node.js 테스트 러너 | 설치 일치성 판단, 실패 및 재시도 |
| npm CLI (`npm ci`, `npm ls`) | lockfile 기반 설치 및 실제 패키지 버전 |
| 격리된 생성 Loop | 실제 초기화, 업데이트 및 실행 경로 |
| `/tmp` 테스트 환경 | 파일시스템 격리, 기존 인스턴스와 독립적인 검증 |
| 런타임 파일 및 프로세스 검사 | 설치 파일, 설치 기록, 실제 실행 동작 |
| 기존 저장소 테스트 | 변경된 영역과 기존 동작의 회귀 여부 |
| Local Smoke Run | 의존성 준비 이후 Operator, Local Task Store, Symphony의 통합 동작 |

검증에서는 의존성 선언 파일의 동기화, 의존성 설치 성공, 실제 실행에서의 사용을 서로 구분한다.

외부 리뷰 서비스의 설치 및 설정은 작업 범위 밖이다. 해당 서비스 없이 수행할 수 있는 Local Smoke Run으로 관련 런타임 통합 동작을 검증하며, 환경 제약으로 실행하지 못한 경로가 있다면 그 사실과 남은 불확실성을 명시한다.
